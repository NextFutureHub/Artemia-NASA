#Artemia — техническое задание на веб-приложение

Версия 1.0 · 13 ноября 2026 года · React + Supabase

Рабочее название Artemia. Документ описывает проект для NASA Space Apps: подготовленный к офлайн-работе персональный журнал здоровья экипажа и наземную панель врача. Это спецификация демонстрационного прототипа, а не сертифицированной медицинской системы. Все демонстрационные профили и истории синтетические. Связь с NASA означает использование открытых материалов, а не одобрение продукта агентством.

## 1. Назначение и критерий успеха

Приложение помогает члену экипажа быстро фиксировать самочувствие, сохранять измерения с указанием их качества, замечать изменения в доступной истории и передавать врачу структурированный отчёт при восстановлении связи.

Главный сценарий: подготовленное устройство → потеря интернета → ежедневная запись → измерение → сохранение → перезапуск приложения → восстановление связи → подтверждённая доставка → просмотр врачом → ответ врача.

Ценность для демонстрации: жюри наблюдает реальную непрерывность работы, понятное происхождение данных и разграничение доступа. Отдельный экран с десятками графиков не считается завершённым продуктом.

Приложение не ставит диагноз, не рассчитывает дозировки, не рекомендует гормональные препараты, не прогнозирует беременность и не определяет пригодность к работе по собственному алгоритму. Оно не обещает обнаружить заболевание. Возможности этого документа не предполагают доступ к персональным медицинским данным реальных астронавтов.

## 2. Приоритеты и границы разработки

Обозначения: P0 — обязательный работающий вертикальный сценарий; P1 — следующий этап после приёмки P0; P2 — развитие за пределами хакатонной версии. Все требования внутри раздела наследуют его приоритет, если не указано иначе.

| Приоритет | Входит | Условие готовности |
|---|---|---|
| P0 | Вход, подготовка одного устройства астронавта, локальные записи, адаптивная форма, встроенный персональный раздел, история, ручные измерения, отчёт, синхронизация, две роли: астронавт и врач, синтетическая миссия, проверяемый доступ | Сценарии приёмки P0 проходят на двух устройствах |
| P0 | Правила качества и полноты данных, объяснения, источники, резервная демонстрация | Каждая подсказка имеет воспроизводимую причину; симуляция обозначена |
| P1 | ESP32 по USB, PWA-установка, командир, интерфейс администратора, официальные назначения врача, настройка миссий через UI, казахский перевод | Реализовано после устойчивой работы P0 |
| P2 | Проверенные клинические правила, реальные медицинские данные, шифрование локального медицинского хранилища с управлением ключами, интеграции медицинских приборов, мобильная аппаратная поддержка, адаптация C# | Отдельный проект с профильной экспертизой и проверкой безопасности |

Для выступления с физическим прибором соответствующая часть P1 становится обязательной: либо проверенная USB-интеграция, либо явно обозначенная запись демонстрации. Нельзя выдавать генератор показаний за подключённый датчик.

В P0 два интерфейса: «Борт» для астронавта и «Медицинский центр» для врача. Настройку пользователей выполняют миграции и отдельный служебный скрипт. Переключателя произвольных ролей в рабочем приложении нет.

## 3. Архитектура и окружения

### 3.1. Технологии

| Слой | Решение | Ответственность |
|---|---|---|
| Интерфейс | React + TypeScript + Vite | Маршруты, формы, локальные состояния |
| Компоненты | Tailwind CSS, доступные примитивы Radix/shadcn | Единая система компонентов; версии фиксируются lock-файлом |
| Формы | React Hook Form + Zod | Единая проверка на клиенте; сервер повторяет критические проверки |
| Локальная БД | IndexedDB через Dexie | Записи, черновики, разрешённые справочники, очередь операций |
| Облачный бэкенд | Supabase PostgreSQL + Auth + RPC | Доступ, серверная валидация, транзакции и хранение |
| Обновление панели врача | Supabase Realtime + повторное чтение API | Сигнал об изменениях; Realtime не является источником истины |
| Сложные служебные операции | Supabase Edge Functions | Приглашения и администрирование; не нужны для локального сохранения |
| Офлайн-оболочка | Локальный production build в P0; Service Worker в P1 | Открытие интерфейса без внешней сети |
| Аппаратный ввод | USB Serial, ESP32, отдельный адаптер | Передача измерений без облака и Wi-Fi |

Выбор вспомогательных библиотек — проектное решение, не утверждение об их необходимости. Новые зависимости не добавлять ради одного простого элемента.

### 3.2. Запуск

Бортовой P0: собранные статические файлы обслуживаются локальным HTTP-сервером на фиксированном origin, например http://localhost:4173. Запускается production build, не dev-сервер с внешними зависимостями. Порт не меняется: IndexedDB привязана к origin. Локальный сервер остаётся запущенным при отключении интернета.

Наземная панель: HTTPS-хостинг той же сборки или отдельный entry point, соединённый с тем же демонстрационным Supabase-проектом. На втором устройстве используется отдельная учётная запись врача. Корпоративный/домашний Wi-Fi врача не отключается вместе с ноутбуком астронавта.

PWA P1: после первого онлайн-входа и проверки ресурсов приложение может открываться с того же origin без сети. Самая первая установка без интернета не поддерживается. Шрифты, CSS, иконки, переводы и справочные выдержки поставляются локально; CDN не используется в критическом пути.

В Supabase хранится только то, что пользователь явно завершил и разрешил передать. Черновики и неподтверждённые измерения не отправляются. Онлайн-вход нужен для подготовки устройства и обновления облачной сессии; заполнение подготовленного дневника не блокируется истечением JWT.

Окружения: development, demo и production-placeholder. Реальные медицинские данные не допускаются в development/demo. У каждого окружения свои ключи, project_id и набор seed-данных. Переменная окружения не даёт пользователю полномочия; права проверяет сервер.

### 3.3. Разделение кода

src/app — маршруты, провайдеры, оболочка; src/features — checkin, measurements, reports, sync, doctor, profile, evidence; src/domain — типы, правила, форматирование; src/data/local — IndexedDB; src/data/remote — Supabase; src/services — очередь, подготовка устройства, отчёты; src/devices — serial и simulator; src/i18n — тексты; supabase/migrations — SQL; supabase/tests — проверки доступа; tests/e2e — пользовательские сценарии.

Компоненты не обращаются к Supabase напрямую. Чтение борта идёт через локальный repository; сохранение — через domain service. Синхронизация независима от открытой страницы. Генератор демоданных подключается только в demo-сборке.

Командир не видит симптомы, пульс, цикл, лекарственные записи, число чувствительных событий, причины обращения к врачу и медицинский индекс. Его экран получает отдельную разрешённую проекцию, а не скрывает колонки загруженной медицинской таблицы.

Администратор приложения не равен владельцу Supabase-инфраструктуры. Владельцы БД технически могут иметь более широкие права; в прототипе не заявлять защиту медицинских данных от владельца инфраструктуры. Минимизировать число владельцев проекта.

### 4.2. Включение персональных вопросов

Пол не является единственным автоматическим переключателем. В профиле поле «Пол для медицинского контекста» необязательное; отдельно задаётся настройка «Показывать вопросы о менструальном и репродуктивном здоровье». При выборе женского пола интерфейс может предложить её включить, но не активирует без подтверждения. Любой пользователь может самостоятельно включить или отключить настройку.

Отключение скрывает будущие вопросы и не удаляет историю. Сбор сведений доброволен. Для каждого вопроса предусмотрены «Не знаю» или «Не хочу отвечать», когда это уместно. Неответ не превращается в отсутствие симптома.

В P0 есть два режима чувствительного раздела: «Только на этом устройстве» и «Передавать назначенному врачу». По умолчанию — только на устройстве. Общая часть завершённой записи синхронизируется, если пользователь включил медицинский обмен при подготовке; чувствительная передаётся только после явного выбора для этой записи. Глобальное разрешение предзаполняет выбор, но итоговый экран всегда показывает его.

Отзыв разрешения онлайн запрещает дальнейшее чтение чувствительных данных врачом через API. Уже прочитанные или выгруженные сведения невозможно гарантированно отозвать. Врач в P0 не хранит медицинскую панель офлайн; HTTP-кэш медицинских ответов запрещён, данные из памяти очищаются при выходе. На других открытых вкладках доступ перепроверяется при фокусе и не реже одного раза в 60 секунд. При отзыве офлайн статус: «Отзыв сохранён на устройстве. Ограничение на сервере вступит в силу после связи». Никаких обещаний мгновенного удалённого отзыва без сети.

## 6. Общая компоновка и дизайн

### 6.1. Визуальный язык

Продукт выглядит как спокойная рабочая система миссии. Основная тема тёмная: фон #0B1220, поверхности #111D2E, основной текст #F4F7FB, вторичный #A8B7CA, акцент #58D6C7. Янтарный обозначает внимание/ожидание, красный — ошибку или пользовательский запрос помощи. Цвет никогда не единственный носитель смысла. Сочетания проверить на контраст до выпуска.

Шрифт локальный Inter или системный sans-serif; числовые значения — tabular numerals. Основной текст 16 px, подписи не меньше 14 px, заголовок страницы 28–32 px. Сетка 8 px; скругление карточек 12 px; границы тонкие. Иконки одного набора, всегда с подписью у ключевых действий. Запрещены декоративные вращающиеся планеты, бегущие цифры, ложные «живые» графики и неконтролируемая пульсация.

P0 проверяется на ноутбуке 1366×768 и экране 1920×1080. На 768 px боковое меню сворачивается; на 390 px формы идут в одну колонку, таблицы заменяются карточками. Аппаратная USB-функция гарантируется только для проверенного desktop-браузера.

### 6.2. Оболочка

Слева меню шириной 232 px: логотип/название, секции, внизу «Источники», «Настройки», «Выйти». Верхняя панель: название миссии, день миссии, UTC-время, статус соединения с сервером, счётчик очереди, позывной. Высота 64 px. День миссии считается от стартовой даты в UTC: floor((now − start)/86400)+1; до старта отображается «До старта N дней».

Статусы соединения: «Сервер доступен», «Нет связи с сервером», «Нужен повторный вход», «Проверяем связь». Зелёный статус не означает здоровье экипажа. navigator.onLine — только подсказка; реальная доступность определяется успешным API-запросом. Клик на статус открывает /onboard/sync. На панели врача показывается время последнего успешного обновления.

В demo-окружении на всех экранах постоянная компактная метка «ДЕМО · синтетические профили». Аппаратный замер реального добровольца обозначается отдельно как «Демонстрационное измерение, не клиническое» и не выдаётся за физиологию синтетического астронавта.

### 6.3. Общие правила компонентов

- Основная кнопка одна на текущую задачу. Название содержит действие: «Сохранить запись», а не «ОК».
- Нажатие блокирует повторный запуск до результата; сохранение имеет idempotency key.
- У каждого поля постоянная подпись; placeholder не заменяет label. Единица рядом с числом; ошибки под конкретным полем.
- Радиокнопки и шкалы без предвыбранного медицинского ответа. Значение 0 допустимо и отлично от null.
- При обязательном пропуске «Продолжить» фокусирует первое поле с ошибкой и показывает общий список ошибок.
- Toast живёт 5 секунд, но важный статус остаётся в записи. Скринридер получает aria-live без озвучивания каждого пакета датчика.
- Черновик сохраняется с задержкой 500 мс после ввода и при смене шага. Надпись «Черновик сохранён на устройстве · HH:MM» только после завершения IndexedDB-транзакции.
- Пустое состояние объясняет следующее действие. Ошибка не заменяется нулём и не стирает старое значение.
- Модальное окно: заголовок, описание последствий, «Отмена», конкретное действие; Esc закрывает только безопасные окна; фокус возвращается на исходную кнопку.
- Внешняя ссылка имеет иконку и открывается отдельно. Без сети: «Для открытия первоисточника нужен интернет», локальная выдержка остаётся доступна.
- Русский и английский интерфейсы P0; все строки в i18n, переключение не сбрасывает форму. Казахский P1. Пользовательский текст не переводится автоматически.
- Дата в интерфейсе зависит от локали; рядом с медицинскими событиями явно указана зона времени. В БД UTC. Период самоотчёта хранится отдельно от timestamp.

## 7. Экран входа и подготовка устройства — P0

### 7.1. /login

Левая часть: название, фраза «Наблюдение за здоровьем экипажа при ограниченной связи», три коротких пояснения. Правая: карточка входа.

| Элемент | Тип и правила | Действие |
|---|---|---|
| Электронная почта | email, обязательно, trim, до 254 символов | Проверка формата |
| Пароль | password, обязательно; не изменять пробелы автоматически | Кнопка «Показать пароль» переключает маску |
| Войти | Primary | Supabase Auth; при успехе маршрут по назначенной роли |
| Забыли пароль? | Ссылка | Онлайн-запрос восстановления; одинаковый ответ независимо от существования email |
| Язык | RU/EN | Меняет интерфейс |
| Открыть подготовленный журнал | Только при наличии локального профиля | Офлайн-режим существующего устройства без изменения облачных прав |

Саморегистрация отключена. Ошибка входа: «Не удалось войти. Проверьте данные или соединение». Сетевую ошибку можно уточнить без раскрытия аккаунта. В P0 локальный журнал содержит только синтетические данные; локальный вход не считается защищённой медицинской аутентификацией. До реального использования нужна отдельная защита устройства и ключей. Нельзя просто кешировать JWT и считать это бессрочным разрешением на сервер.

### 7.2. /prepare

Мастер из трёх шагов. Один бортовой origin хранит одного астронавта. Для другого пользователя требуется синхронизация/экспорт очереди и очистка локального профиля.

Шаг 1 «Проверьте профиль»: позывной, имя, миссия, назначенный врач, период миссии — read-only из сервера. «Это мои данные» обязательно. «Сообщить об ошибке» показывает контакт организатора без отправки произвольного письма.

Шаг 2 «Настройте журнал»: язык; часовой пояс отображения; предпочтительное время ежедневного напоминания HH:MM; персональные вопросы on/off; режим чувствительных данных; чекбокс «Передавать завершённые общие записи назначенному врачу». В демо передача общих записей нужна для основного сценария, но пользователь видит последствия выбора. Напоминание P0 работает только при открытом приложении; не обещать фоновые push.

Шаг 3 «Подготовьте устройство»: список проверок «Интерфейс доступен», «Локальное хранилище доступно», «Профиль загружен», «Справочники загружены», «История загружена», «Правила загружены», «Назначение врача проверено». Для PWA дополнительно «Офлайн-ресурсы сохранены». Каждая строка имеет статус и кнопку «Повторить» при ошибке. Кнопка «Загрузить и проверить» выполняет подготовку; «Начать работу» активна после обязательных проверок. Если сервер недоступен при первой подготовке, полноценного запуска нет.

При недоступной IndexedDB: «На этом устройстве невозможно надёжно сохранить журнал»; завершение записи запрещено, ввод можно скопировать из черновика. При малом объёме хранилища предупреждение; очередь не удаляется автоматически.

## 8. «Сегодня» — /onboard/today, P0

Порядок сверху вниз:

1. Заголовок «Сегодня», дата, подпись «Ваш журнал на этот день».
2. Главная карточка «Самочувствие»: ещё не заполнено / черновик / завершено. Основная кнопка соответственно «Заполнить», «Продолжить», «Открыть запись». В завершённом состоянии вторичная «Добавить запись» для изменения самочувствия в тот же день; новое событие не перезаписывает утреннее.
3. Карточка «Последнее измерение»: пульс или «Измерений пока нет», единица, время, источник, качество. Кнопка «Измерить» ведёт на измерения. Если значение устарело по настройке интерфейса, текст «Последнее измерение X назад», не «Текущий пульс».
4. Карточка «На что обратить внимание»: максимум 3 нерешённых события качества/полноты/изменений. Каждое содержит заголовок, объяснение, время, «Почему?» и конкретное действие. При пустом состоянии «Новых подсказок нет»; не «Вы здоровы».
5. Карточка «Связь с врачом»: последний ответ, время его получения; кнопка «Открыть». Если ответа нет: «Ответов пока нет». Отдельно доставка: N операций ожидают связи.
6. Лента последних 5 событий: запись, измерение, сформирован отчёт, подтверждена доставка, просмотр врачом. Личные чувствительные подробности в заголовки общей ленты не выводятся.

Кнопка «Связаться с медиком» доступна постоянно. Открывает окно с выбором «Подготовить сообщение» или «Показать бортовой порядок обращения». Второе открывает заранее заданный миссией текст контакта/действий без диагностических инструкций. При отсутствии такого материала: «Порядок обращения для этой миссии не настроен». Приложение не обещает экстренную доставку сообщения без связи.

## 9. Форма самочувствия — /onboard/checkin/new, P0

Пять логических шагов: «Общее» → «Симптомы» → «Персональные вопросы» (если включены) → «Измерения» → «Проверка». Верхний stepper показывает фактическое число шагов. Слева/сверху прогресс, справа компактная подсказка о локальном сохранении. Внизу закреплены «Назад», «Сохранить черновик и выйти», «Продолжить». На первом шаге «Назад» заменяется «Отмена» с сохранением черновика. Перед уходом с несохранённым вводом предупреждение.

Форма привязана к конкретному draft_id. Повторное открытие восстанавливает тот же черновик. На борту один активный черновик самочувствия; «Добавить запись» при существующем черновике предлагает продолжить или удалить его после подтверждения.

### 9.2. Шаг «Симптомы»

Первый вопрос: «Есть ли симптомы, которые вы хотите отметить?» — «Нет», «Да», «Не хочу отвечать». Если «Нет» или пропуск, список скрывается; ранее введённые значения при переключении не стираются без предупреждения «Удалить ранее добавленные симптомы из этой записи?».

При «Да»: кнопки выбора «Головная боль», «Головокружение», «Тошнота», «Дискомфорт в животе», «Боль в мышцах/суставах», «Ощущение сердцебиения», «Другое». Список — словарь версии, а не диагностическая классификация.

Каждый выбранный симптом создаёт отдельную раскрытую карточку:

| Поле / кнопка | Правила |

| Когда началось | «Сейчас», «Сегодня раньше», «Более суток назад», «Не знаю» |

При необходимости немедленной помощи используйте бортовой порядок обращения».

### 9.4. Шаг «Измерения»

Показывает все доступные локальные измерения за выбранный день: вид, число/единица, время, источник, качество. Checkbox «Прикрепить» доступен только для завершённого измерения; плохое качество можно приложить как неудачную попытку, но не использовать как числовое основание подсказки.

Кнопки «Новое измерение» открывает встроенную панель страницы измерений с возвратом в форму; «Ввести вручную» открывает ручную форму; «Продолжить без измерений» допустима всегда. Пустая карточка: «Измерения необязательны. Запись самочувствия можно сохранить отдельно».

Нельзя автоматически прикреплять старый пульс как текущий. Каждая связь содержит measurement_id; исходное измерение не копируется с потерей происхождения.

### 9.5. Шаг «Проверка и сохранение»

Блоки: время и тип записи; общее состояние; симптомы; прикреплённые измерения; свёрнутая чувствительная часть с явным получателем; запрос врачу. Рядом с каждым «Изменить» возвращает на нужный шаг без потери остальных данных.

Три строки доставки: «Общая часть: назначенному врачу / только устройство», «Персональный раздел: …», «Связь: доступна / отсутствует». Если общая передача выключена, пользователь может включить её для записи; чувствительная отправка требует общего медицинского обмена, иначе объяснение и выбор сохранить только локально.

Кнопка «Сохранить запись» выполняет одну локальную транзакцию: неизменяемая ревизия + связи измерений + разрешённые outbox-операции + журнал локального события. Только после commit показывать успех. Черновик помечается завершённым. Облачный сбой не отменяет локальный успех.

Экран результата: «Запись сохранена на устройстве», время, «Ожидает передачи» либо «Получена сервером», кнопки «Открыть запись», «Подготовить отчёт», «На сегодня». Если пользователь выбрал только локальное хранение, текст «Хранится только на этом устройстве» вместо ошибки синхронизации.

### 9.6. Просмотр и исправление записи

Заголовок, дата, версия, способ ввода, статус доставки. Секции соответствуют проверке. Кнопки «Дополнить / исправить», «Создать отчёт», «Показать версии». Исправление создаёт новую ревизию с обязательной причиной до 300 символов, не меняет исходник. Уже отправленный отчёт остаётся неизменным; рядом появляется «Есть более новая версия записи». Новая ревизия не передаёт ранее локальную чувствительную часть без нового разрешения.

Завершённые записи не удаляются обычной кнопкой. Действие «Пометить ошибочной» требует причины, создаёт событие аннулирования; исходные данные сохраняются в истории и исключаются из тенденций. Реальное удаление персональных данных — отдельная процедура вне P0, не имитируется скрытием карточки.

## 10. Измерения — P0 ручной ввод, P1 USB

Верх: название «Измерения», вкладки «Новое»/«История». Карточка способа: «Вручную», «USB-датчик», «Симулятор» (только demo). Видимый источник обязателен в результатах, графиках и отчётах.

### 10.1. Ручное измерение

| Поле | Правило |
|---|---|
| Показатель | Пульс / Температура тела / SpO₂; обязательно |
| Значение | Пульс 20–250 целое уд/мин; температура 30–45,0 °C шаг 0,1; SpO₂ 50–100 % целое |
| Время | Обязательно, по умолчанию сейчас; ограничение будущего +5 минут |
| Контекст | В покое / После нагрузки / Другое / Не указан |
| Прибор/способ | Необязательный текст до 100 символов; «Не указан» по умолчанию |
| Примечание | До 300 символов |
| Сохранить измерение | Локальное сохранение с quality=unknown, source=manual |

Диапазоны — техническая защита от опечаток для демо, не диапазоны нормы и не критерии здоровья. При выходе: «Значение вне поддерживаемого диапазона ввода. Проверьте единицы; исходное наблюдение можно описать в комментарии». Не обрезать число до ближайшей границы. Ручной ввод не получает статус «Подтверждено датчиком».

### 10.2. USB-панель

Поддерживаемая конфигурация выступления: проверенный desktop Chrome/Edge, secure context localhost/HTTPS, ESP32 по USB. При отсутствии navigator.serial вместо ошибки: «USB-подключение недоступно в этом браузере. Доступен ручной ввод». Разрешение порта запрашивается только по нажатию.

Карточка устройства: имя, firmware_version, device_id, соединение, последний пакет, источник «USB». Кнопки «Подключить», «Отключить», «Начать измерение», «Отменить». «Начать» активна при подключённом совместимом устройстве и отсутствии другого измерения.

Состояния: disconnected → connected → waiting_contact → collecting → evaluating → result_valid / result_invalid. Разрыв на любом активном этапе ведёт в interrupted, без фиктивного результата. «Повторить» создаёт новый attempt_id, предыдущая попытка сохраняется как техническое событие.

Во время сбора: инструкция «Положите палец и держите его неподвижно», таймер 30 секунд, индикатор контакта, график исходного сигнала с подписью «Оптический сигнал PPG» (не ЭКГ), текст качества. Кнопка «Сохранить результат» появляется после завершения и ручного подтверждения. Во время потока ничего не отправляется на сервер.

Контракт JSON Lines: protocol_version, device_id, firmware_version, session_id, seq, uptime_ms, contact_detected, raw_ir, raw_red (если доступен), hr_bpm nullable, quality_flags[]. Один JSON на строку, UTF-8, максимальная длина строки 4 KB. Часы события добавляет браузер; uptime не является UTC. Неизвестная версия протокола блокирует начало и показывает понятную ошибку.

Новый seq принимается один раз в пределах session_id. Неполная строка буферизуется до newline. Некорректная строка игнорируется с техническим счётчиком; после 5 последовательных ошибок сессия прерывается. Если 2 секунды нет пакетов, график останавливается и появляется «Нет новых данных»; прежний пульс не показывается как текущий.

Алгоритм качества Q1: без контакта, с флагом насыщения, с разрывом >2 секунд или недостаточным числом пригодных оценок — invalid/insufficient. Для демо пригодный результат требует минимум 20 секунд контакта в 30-секундном окне, минимум 10 ненулевых пригодных оценок HR, отсутствия saturation; итог — медиана пригодных оценок. Пороговые параметры и версия алгоритма сохраняются. Эти критерии проверяют полноту и грубые артефакты, не доказывают медицинскую точность. Если устройство не умеет выдавать нужные признаки, quality=unknown; не рисовать «Высокое качество».

Сдвиг пальца не обязан всегда обнаруживаться; на презентации нельзя обещать распознавание любого движения. Сценарий качества заранее проверяют на реальном приборе. MAX30102 в первой аппаратной версии используется для пульса/PPG; SpO₂ с него не демонстрируется как достоверное измерение без отдельной валидации.

Карточка результата: значение, единица, время, метод, quality, объяснение, «Сохранить», «Повторить», «Закрыть без сохранения». При invalid числовой итог скрыт, остаётся «Не удалось получить пригодное измерение»; «Сохранить попытку» фиксирует неудачу без числового значения. Если подключён прибор другого добровольца, измерение остаётся в отдельном демонстрационном профиле, не смешивается с историей астронавта.

Симулятор имеет постоянную подпись «СИМУЛЯЦИЯ». Профили «Стабильный сигнал», «Потеря контакта», «Разрыв потока»; результат source=simulated. Он тестирует UI и очередь, не считается тестом аппаратного качества.

## 11. История и тенденции — P0

Экран /onboard/history: сверху диапазон «7 дней / 30 дней / Весь период / Выбрать даты»; поля «С» и «По» в пользовательской зоне; кнопка «Применить». Начало не позже конца. Дефолт 7 дней. Фильтр типа «Все / Самочувствие / Измерения / Отчёты / Ответы». Фильтр источника «Все / Ручной / Устройство / Симуляция».

Первый блок — графики сна, усталости и пульса, каждый отдельной карточкой. Ось X — время; Y с единицей и явным диапазоном. Не соединять линией большие пропуски. Невалидные попытки показаны отдельными значками под графиком и не участвуют в среднем. Ручные значения отличаются маркером от приборных, симуляция — подписью и штриховым стилем. Tooltip содержит точное время, значение, источник, качество и ссылку на исходник. Нет общего нормализованного графика, смешивающего несопоставимые единицы.

Ниже список событий по убыванию времени: дата, тип, короткое содержание, источник, локальный/доставленный статус. Нажатие открывает запись. «Загрузить ещё» подгружает следующие 25 локальных событий. «Поиск в комментариях» не входит в P0, чтобы не создавать лишнюю индексацию чувствительного текста.

Личная тенденция P0 — описательная статистика. Для выбранного показателя сравнивается последнее пригодное наблюдение с медианой предыдущих 7 суток при наличии минимум 5 наблюдений на минимум 3 разных днях. Отбор учитывает одинаковые единицы; приборный и ручной источники не объединяются автоматически. Выборка и контекст показываются в «Как рассчитано». Если данных мало: «Недостаточно истории для сравнения». Надпись «Личная медиана» не заменяется словом «Норма».

Для сна берётся последняя неаннулированная ежедневная запись на дату, чтобы дополнительные записи не увеличивали вес дня. Пропуски не заменяются нулём. Для пульса сравниваются только сохранённые пригодные значения в покое из сопоставимого источника. Нельзя выводить риск заболевания из тренда. Пороговая подсветка медицинских рисков отсутствует в P0.

Чувствительная история открывается отдельной вкладкой «Персональные записи» только у владельца или разрешённого врача; не попадает в общий tooltip. Сводный календарь цикла P1 показывает только введённые даты и события, без предсказания.

## 12. Подсказки и объяснения — P0

Название раздела «Наблюдения и качество данных», а не «Диагнозы». Три типа: действие пользователя, техническое качество, описательное изменение. Не вводить процент уверенности, если он не получен из валидированной модели.

| rule_id | Условие | Текст | Действие |
|---|---|---|---|
| DATA_CONTACT_LOST_V1 | Попытка завершена без контакта/с прерыванием | «Измерение не завершено» + фактическая причина | «Повторить измерение» |
| DATA_NO_CURRENT_V1 | В записи нет прикреплённого измерения | «Запись сохранена без измерений» | «Добавить измерение»; информационный, не тревога |
| SELF_REVIEW_REQUEST_V1 | Пользователь явно попросил внимание врача | «Вы запросили просмотр записи» | «Подготовить отчёт» |
| SYNC_AUTH_REQUIRED_V1 | Сервер вернул отказ из-за истёкшей сессии после попытки refresh | «Для отправки нужен повторный вход» | «Войти» |
| HISTORY_CHANGE_V1 | Доступно сравнение по правилам раздела 11 | «Показатель отличается от вашей предыдущей медианы на X» | «Посмотреть историю» |

HISTORY_CHANGE не создаёт клинической срочности; по умолчанию показывается только в истории. На главную выносится по явному действию «Закрепить наблюдение». В P0 нет автоматической красной тревоги на основании общего самочувствия, выделений или изменения пульса.

Карточка объяснения: заголовок; конкретные входные данные со ссылками; timestamp вычисления; версия правила; результат; ограничение; источник, если он обосновывает контекст. Если правило инженерное, указать «Правило прототипа». Нельзя прикреплять NASA-источник так, будто NASA утвердило наши числовые пороги.

«Отметить просмотренным» записывает acknowledge события, но не исправляет неудачное измерение и не закрывает запрос врачу. «Скрыть с главной» — только предпочтение отображения. Медицинский статус из этого не выводится.

## 13. Отчёты и обмен с врачом — P0

### 13.1. Создание отчёта

Вход из записи, истории или списка отчётов. Модальное окно/отдельная страница:

| Поле | Правило |
|---|---|
| Название | До 120 символов, по умолчанию «Самочувствие · дата» |
| Период | Сегодня / 7 дней / Выбрать даты; не включает будущее |
| Записи | Список с checkbox; минимум одна запись или одно измерение |
| Получатель | Назначенный врач, read-only; при отсутствии назначения отправка запрещена, локальный черновик допустим |
| Причина | Плановый отчёт / Прошу посмотреть / Ответ на запрос врача |
| Сообщение | Необязательно, до 2000 символов |
| Общая часть | Список включаемых типов и количество записей |
| Персональный раздел | По умолчанию выключен; включение только для записей с разрешённой передачей и отдельным подтверждением |
| Предпросмотр | Открывает точный состав будущего отчёта |
| Сохранить и поставить в очередь | Создаёт неизменяемый snapshot и outbox |

Предпросмотр показывает получателя, выбранные версии, время среза, ограничения качества. Пользователь может открыть каждое исходное событие. Приложение не дописывает медицинские заключения. Сводка генерируется детерминированным шаблоном, без облачного LLM: «За период заполнено N записей. Запрос просмотра: да/нет. Прикреплено N измерений, из них N с неизвестным качеством». Чувствительные поля не попадают в общую сводку.

Отчёт состоит из общей и отдельной чувствительной частей. Права доступа не задаются одним JSON-флагом внутри общей строки. Каждая часть имеет отдельный hash; общий hash и доступный командиру/администратору статус не раскрывают содержимое чувствительной части. Hash — контроль целостности передачи, не цифровая подпись и не доказательство медицинской достоверности.

### 13.2. Статусы

Три независимых поля:

1. Локальная готовность: draft / finalized / superseded.
2. Доставка: local_only / queued / sending / accepted / failed / blocked_auth / conflict.
3. Работа врача: not_opened / opened / replied.

«Получен сервером» присваивается только по ответу RPC с receipt_id и accepted_at. «Открыт врачом» — только после успешной загрузки отчёта врачом и отдельного серверного acknowledge. «Ответ получен» — после загрузки ответа на борт. Realtime-событие и галочка в интерфейсе не подменяют receipt. Если сервер принял, а клиент потерял ответ, повторная отправка возвращает тот же receipt.

### 13.3. Список и карточка

/onboard/reports: фильтры «Все / Ожидают передачи / Получены сервером / С ответом»; карточки: название, период, получатель, статусы доставки и просмотра, последняя активность. «Создать отчёт» вверху справа. Нажатие открывает карточку.

Карточка отчёта: название и ID; лента «Сохранён → Получен сервером → Открыт врачом → Ответ доставлен» с реальными временами, незавершённые этапы серые; вкладки «Содержание», «Ответы», «Доставка». Кнопки «Повторить отправку» при retryable-ошибке, «Создать дополнение», «Печатная версия». Отправленный snapshot не редактируется; дополнение — новый отчёт со ссылкой на предыдущий.

«Печатная версия» открывает локальную print-friendly страницу с датой, версиями, источниками, качеством и пометкой демо. Перед включением персональных разделов отдельное подтверждение. Файлы автоматически в Supabase Storage не отправляются. На общедоступном компьютере экспорт реальных данных не предполагается.

## 14. Панель врача — P0

### 14.1. /ground/inbox

Врач работает онлайн. При потере сети баннер «Нет связи. Показан срез на HH:MM»; уже загруженное остаётся только в памяти с видимой давностью. Новое отправление ответа и подтверждение просмотра недоступны; введённый ответ сохраняется в памяти текущей вкладки с предупреждением, что закрытие потеряет черновик. Медицинский offline-кэш врача в P0 не реализуется.

Верх: фильтр миссии из назначений, «Обновить», время успешного обновления. Три счётчика: «Новые отчёты», «Запрошен просмотр», «Ответ отправлен». Это рабочая очередь, не автоматическая медицинская сортировка по тяжести.

Фильтры: пациент по позывному/имени, период, «Все / Не открыты / Открыты / С ответом», «С запросом просмотра». Список строк: позывной; название отчёта; период; requested_review; время поступления; статус. Сортировка: запросы просмотра выше, затем дата поступления; подпись «Порядок по запросам пользователей, не клинический триаж». Нажатие ведёт на отчёт.

Справа необязательная панель выбранного пациента: позывной, миссия, дата последней доставленной записи, кнопка «Карточка пациента». Нет «живого состояния», если последняя запись устарела.

### 14.2. /ground/crew/:id

Шапка: имя, позывной, миссия, активность назначения. Вкладки «Обзор», «История», «Отчёты», «Персональные данные» (только при разрешении). Обзор показывает последние доставленные сведения и возраст каждого источника. Отдельно «На устройстве могут быть ещё неотправленные записи» — сервер не знает их содержания и количества без отдельного технического heartbeat; в P0 число не выдумывается.

P1 блок «Параметры наблюдения»: врач задаёт персональный reference note и ориентиры только как документированную настройку после медицинского согласования. P0 отображает лишь описательную медиану, не редактируемые клинические пороги.

### 14.3. /ground/reports/:id

Слева содержание отчёта, справа карточка ответа. Сверху receipt, версия, получено_at и статус целостности. После успешной полной загрузки общей части клиент вызывает mark_report_opened; открытие чувствительной части фиксируется отдельно и не считается состоявшимся при отказе доступа.

Карточка ответа имеет заголовок «Ответ члену экипажа»:

| Поле / кнопка | Правило |
|---|---|
| Получатель | Автор отчёта, read-only |
| Тип ответа | Подтверждение получения / Уточняющий вопрос / Комментарий |
| Текст | Обязательно 1–3000 символов |
| Связанная запись | Необязательный выбор из включённых в отчёт |
| Видимость | Только пациент и назначенный врач; если ответ касается чувствительных данных — обязательная отметка «Чувствительная часть» |
| Предпросмотр | Показывает адресата и текст |
| Отправить ответ | Онлайн RPC, блокировка повторного клика; после commit статус «Сохранён на сервере, ожидается получение устройством» |

Приложение не генерирует врачебный совет. Для демонстрации используется нейтральный заранее согласованный текст: «Отчёт получил. Уточните, когда началось изменение самочувствия». Доставка ответа на борт подтверждается отдельным receipt; серверная запись ответа не означает, что астронавт его прочитал. Астронавт нажимает «Прочитано» — явное подтверждение.

Врач не редактирует исходные ответы астронавта. Ошибочный ответ исправляется новым комментарием со ссылкой на предыдущий, не удаляется бесследно. В P0 нет прикрепления произвольных файлов и лекарственных назначений.

## 15. Профиль, настройки, миссии

### 15.1. Профиль астронавта — P0

Секции «Основное», «Настройки журнала», «Приватность», «Устройство».

| Поле | Тип / редактирование |
|---|---|
| Имя и позывной | Read-only в P0; администратор задаёт при подготовке |
| Миссия, дата старта/окончания | Read-only |
| Назначенный врач | Read-only; активность назначения из последнего среза |
| Возраст | Необязательное целое 18–100 для синтетического взрослого профиля; дата рождения в P0 не собирается |
| Пол для медицинского контекста | Женский / Мужской / Интерсекс / Не указывать; необязательно |
| Рост / масса | P1; в P0 не собирать без использования |
| Язык | RU/EN |
| Часовой пояс | Поиск IANA-зоны; значение по умолчанию UTC для миссии |
| Время напоминания | HH:MM; переключатель вкл/выкл; работает при открытом приложении |
| Персональные вопросы | Вкл/выкл с пояснением последствий |
| Контекст цикла | Те же варианты, что в форме; необязательно; не выводить в обычной карточке профиля |
| Обмен общими завершёнными записями | Вкл/выкл; отключение влияет на новые записи, не удаляет отправленные |
| Разрешение на чувствительные сведения | Только локально / Передавать врачу; изменение фиксируется событием |

«Сохранить настройки» сохраняет локально и ставит разрешённые операции в очередь. Онлайн-изменения назначения врача не инициируются астронавтом. Смена часового пояса меняет отображение, но не UTC-время старых событий и не их изначальную дату самоотчёта.

«Очистить устройство»: окно показывает число неотправленных операций. При ненулевом числе действие заблокировано до синхронизации либо подтверждённого экспорта синтетической резервной копии P0. Подтверждение фразой «ОЧИСТИТЬ»; очищается только локальный профиль, не серверные данные. «Выйти» очищает токены и память; отдельно предлагается оставить подготовленный синтетический журнал или очистить его. На реальных данных такая политика требует переработки.

Локальная резервная копия демо: JSON с version, dataset_id, profile_id, данными и outbox; предупреждение «Файл содержит демонстрационные персональные сведения». Импорт только в demo, с проверкой версии и совпадения владельца; сначала предпросмотр количества событий, затем транзакция. Не считать незашифрованный экспорт пригодным для реальной медицины.

### 15.2. Короткие и длительные миссии

Оболочка и безопасность одинаковы. У миссии явная настройка short/extended, а не клиническая классификация по произвольному порогу дней. В short дефолт истории 7 дней и акцент на текущей записи; в extended — 30 дней, регулярность заполнения и тенденции. Набор полей не расширяется ежедневно автоматически. Персональные вопросы и права одинаковы в обоих режимах. Длительная миссия не включает дополнительные диагнозы.

### 15.3. Командир — P1

На /command только карточки экипажа: позывной, добровольно опубликованное «Доступен / Нужна корректировка нагрузки / Не публиковать», время публикации, срок актуальности, техническая доступность канала при наличии данных. По истечении срока «Статус устарел». «Нужна корректировка» не сопровождается причиной.

Астронавт публикует статус отдельной кнопкой «Операционный статус» на Today. Форма: значение, срок актуальности до 24 часов, предпросмотр «Это увидит командир», «Опубликовать». Никакого автоматического вывода из менструации, усталости или пульса. Отзыв создаёт tombstone и синхронизируется при связи. Командир не может открыть медицинскую карточку по клику.

### 15.4. Администратор — P1

Вкладки «Миссии», «Участники», «Назначения», «Технический журнал». Создать миссию: название 3–80, code 3–20 латиница/цифры/дефис, start_at UTC, end_at > start_at, mode short/extended, default_timezone, текст порядка обращения до 2000, сохранение. Все даты валидируются сервером.

Пригласить пользователя: email, отображаемое имя 1–100, позывной 2–20, роль из разрешённых, миссия. Секретный вызов через Edge Function с проверкой роли администратора; клиент не содержит service_role. Пользователь не может назначить себе роль через metadata.

Назначить врача: выбор активного врача, пациента, дата начала, дата окончания nullable; подтвердить. Отозвать: причина 1–300, предупреждение о прекращении серверного доступа. Ни один администратор не открывает медицинский payload. Служебный лог показывает operation_id, код ошибки, время, компонент, но не комментарии, симптомы и токены.

## 16. Экран связи — /onboard/sync, P0

Вверху три независимые карточки: «Доступность сервера», «Авторизация», «Очередь операций». В каждой текст, время проверки, действие. Кнопка «Проверить связь» выполняет короткий запрос. «Синхронизировать сейчас» запускает worker, но не создаёт копии операций. «Войти повторно» открывает Auth; после входа совпадение user_id обязательно, иначе очередь остаётся заблокированной.

Таблица очереди: тип записи, дата создания, состояние, попытки, последняя ошибка, следующее повторение. Чувствительные значения и даже детальные названия симптомов здесь не выводятся. Для чувствительной операции название «Защищённая медицинская часть», доступ только владельцу. Кнопки строки: «Повторить» для временной ошибки; «Посмотреть причину»; «Разрешить конфликт» если нужно. Кнопки «Пометить доставленным» нет.

Состояния outbox: pending, sending, retry_wait, accepted, blocked_auth, blocked_permission, validation_error, conflict. Успешные операции можно скрыть фильтром, но история квитанций сохраняется.

Тексты:

- Нет сети: «Сохранение на устройстве работает. Передача продолжится после восстановления связи».
- 401 после refresh: «Нужен повторный вход. Записи сохранены».
- 403: «Сервер не разрешил передачу. Проверьте назначение и доступ».
- 422: «Часть записи не прошла проверку. Откройте подробности».
- Квота/429: «Сервер временно ограничил запросы. Повтор запланирован».
- Ошибка хранилища: «Не удалось сохранить на устройстве. Не закрывайте форму».
- Конфликт: «На сервере есть другая версия. Исходные записи сохранены».

## 17. Модель данных

### 17.1. Общие соглашения

UUID генерируется на клиенте для пользовательских событий; серверные квитанции получают отдельный UUID. Все времена timestamptz UTC; local_date — дата самоотчёта; timezone — IANA-строка. created_at_server выставляет сервер, recorded_at — время наблюдения, created_at_device — время локального создания. Не доверять часам устройства для прав доступа или порядка серверной доставки.

Обязательные общие поля событий: id, mission_id, subject_id, author_id, device_id, schema_version, recorded_at, created_at_device, created_at_server nullable до приёма, source, demo_dataset_id nullable. Пользователь не может подставить author_id другого пользователя; сервер выводит его из auth.uid(). Для аппаратных данных subject_id остаётся проверенным владельцем профиля.

Пустое числовое поле = null с отдельным answer_status: answered/unknown/declined/not_applicable. Запрещены магические -1 или 0 для пропуска. Enum-значения стабильны и не зависят от языка.

prepared_profile, mission_cache, assignment_cache, consent_cache, source_cache, rule_cache, drafts, local_checkins, local_checkin_revisions, local_personal_revisions, local_measurements, local_reports, local_personal_reports, local_messages, outbox, receipts, sync_cursors, local_audit, demo_settings.

В локальных таблицах ключи включают owner_id и environment_id; все repository-запросы фильтруют владельца. local_personal_* без разрешения никогда не попадают в outbox. outbox хранит operation_id, owner_id, entity_type, entity_id, payload_version, frozen_payload, payload_hash, dependencies[], state, attempts, next_attempt_at, last_error_code, lease_until. Содержимое операции фиксируется при постановке; исправление — новая операция, а не изменение hash уже отправляемой.

Структурированный клон и JSON сериализация должны сохранять null, Unicode и десятичные значения. Для hash использовать единую канонизацию JSON с сортировкой ключей, UTF-8 и SHA-256 на обеих сторонах; сравнение тестировать на RU/EN-текстах. Hash не защищает от подделки самим автором.

raw PPG хранится локально только для последней подтверждённой демонстрационной попытки, максимум 30 секунд при согласованной частоте. На сервер P0 уходят агрегат, качество и версия алгоритма, не весь поток. Сырые данные удаляются по локальной политике; завершённые записи/outbox не удаляются при очистке графика.

## 18. API, транзакции и синхронизация — P0

### 18.1. Контракты

Supabase SDK используется для Auth, безопасного чтения и RPC. Прямой INSERT/UPDATE критических медицинских таблиц у authenticated запрещён, чтобы нельзя было обойти серверную проверку через REST. Изменения проходят через ограниченные RPC с проверкой auth.uid(), текущих назначений, согласий и схемы.

| RPC / действие | Вход | Выход и гарантии |
|---|---|---|
| get_preparation_bundle | mission_id, known_schema_version | Разрешённый профиль, назначения, справочники, версии; без чужих пациентов |
| submit_operation | operation_id, type, schema_version, payload, hash, dependencies | В одной транзакции проверка, запись события, audit и receipt; accepted/duplicate/conflict/validation_error |
| pull_updates | scope, cursor, limit ≤100 | Только разрешённые события, next_cursor, tombstones; cursor непрозрачный |
| get_report | report_id | Общая разрешённая часть; чувствительная отдельным запросом |
| get_personal_report_part | report_id | Перепроверка назначения и согласия на каждый вызов; аудит доступа |
| mark_report_opened | report_id, operation_id | Серверное время; только назначенный врач |
| post_doctor_message | report_id, operation_id, type, text, visibility | Проверка роли/получателя; append-only |
| acknowledge_message | message_id, stage=received/read, operation_id | Только адресат; received не равно read |
| update_sharing_consent | decision, scope, operation_id, supersedes_id | Новое событие; effective_at_server; отзыв не удаляет историю |
| publish_operational_status P1 | status, expires_at, operation_id | Отдельная запись, без медицинских полей |

submit_operation поддерживает ограниченный allowlist типов: checkin_bundle, measurement, report_bundle, invalidation, profile_preferences, consent_change. Чувствительные части отправляются в том же bundle только при наличии разрешения; каждая часть сохраняется в своей таблице. Локальные поля и лишние ключи отвергаются.

Если security definer необходим для транзакционного RPC: фиксировать search_path, явно проверять пользователя и полномочия, schema-qualify все объекты, revoke EXECUTE FROM PUBLIC/anon, GRANT только нужной роли. Нельзя считать RLS автоматически действующим внутри привилегированной функции.

### 18.2. Порядок отправки

1. При локальном сохранении данные и outbox записываются одной IndexedDB-транзакцией.
2. Один worker на профиль выбирает операцию без незавершённых зависимостей. Несколько вкладок координируются через Web Locks либо lease в IndexedDB; серверная идемпотентность остаётся обязательной.
3. Проверяются доступность, auth и owner_id. Очередь другого пользователя никогда не отправляется от новой сессии.
4. Изменения согласия обрабатываются перед зависящими чувствительными payload. Отзыв блокирует ещё не отправленные чувствительные операции локально сразу. Уже отправляемая операция может быть принята до отзыва; интерфейс честно показывает порядок серверных событий.
5. Сначала сохраняются измерения/записи, затем отчёты со ссылками на принятые версии. Операции unrelated могут продолжаться при ошибке другой записи.
6. После RPC accepted/duplicate квитанция и состояние accepted записываются локально одной транзакцией.
7. Затем загружаются серверные изменения, ответы и события просмотра; cursor продвигается только после успешного локального commit.
8. UI обновляется из локальной БД; подтверждённая доставка не вычисляется по наличию интернета.

Идемпотентность: повтор operation_id с тем же hash возвращает исходную квитанцию без повторных rows; тот же ID с другим hash — conflict, без перезаписи. Уникальный индекс и транзакция защищают от двух параллельных запросов. Ответ сервера содержит проверенный hash; несовпадение отображается как ошибка целостности.

Повторы: 2, 5, 15, 30, 60 секунд с jitter ±20%, далее не чаще раза в минуту при открытом приложении. Уважать Retry-After. 401 — один refresh, затем blocked_auth; 403 — blocked_permission без бесконечных повторов; 422 — validation_error; 409 — conflict. Timeout/5xx — retry. Восстановление после закрытия вкладки возвращает просроченные sending leases в pending.

Фоновая работа при полностью закрытом браузере не гарантируется. При следующем запуске очередь продолжается. В P0 не обещать доставку в фоне средствами Service Worker.

### 18.3. Получение изменений

Realtime сообщает «данные изменились»; после него выполняется разрешённое чтение/pull. Пропуск событий восполняется при входе, фокусе окна, восстановлении сети и раз в 30 секунд при открытой панели врача. Для P0 с малой нагрузкой допустим Postgres Changes только на безопасных таблицах событий с RLS, без медицинского текста в уведомлении. Каналы и payload не публикуются анонимно.

Cursor должен отражать устойчивый серверный порядок. Простая пагинация по created_at клиента запрещена. Реализация P0: серверный журнал изменений с выделением позиции под транзакционной блокировкой на scope и commit до выдачи следующей позиции; изменения согласий/назначений и tombstones тоже попадают в журнал. Альтернатива допустима только с тестом отсутствия потерь при конкурентных транзакциях. Не использовать MAX(sequence) как cursor без решения проблемы коммитов вне порядка.

При отзыве назначения врач теряет доступ немедленно на следующем API-запросе. Realtime не заменяет эту проверку. Борт получает обновлённые назначения; queued-отчёты к старому врачу не перенаправляются молча — status blocked_permission, пользователь выбирает нового получателя при создании нового отчёта.

### 18.4. Конфликты и частичные ошибки

В P0 один основной бортовой писатель на профиль. Проверка parent_revision_id всё равно обязательна. Если серверная текущая ревизия отличается, запись не теряется: показать обе версии с временем и источником. Действия «Оставить серверную» (локальная сохраняется как отклонённая версия) или «Создать дополнение на основе серверной». Автоматического last-write-wins для медицинского содержания нет.

Bundle общей и разрешённой чувствительной частей атомарен: либо весь bundle принят, либо нет. Локально общая часть при этом уже сохранена. Ошибка отправки не должна появляться как ошибка локального сохранения. Независимый отчёт без чувствительной части пользователь может создать отдельно после отказа — приложение не удаляет часть silently.

## 19. RLS и безопасность доступа — P0

RLS включается на всех доступных через Data API таблицах. anon не имеет доступа к медицинским таблицам. profiles раскрывает только собственный профиль и минимальные данные назначенных участников. memberships/assignments изменяются только серверными административными операциями.

Политики медицинского SELECT: subject_id=auth.uid() либо активное medical_assignment текущего врача в соответствующей миссии. Чувствительные SELECT дополнительно требуют действующего разрешения. Политики INSERT/UPDATE/DELETE по умолчанию запрещены; запись через проверенные RPC. Отдельные исключения описать миграциями. Проверка принадлежности применяется ко всем foreign key, не только корневой записи.

Права не берутся из редактируемого user_metadata. Администраторская роль хранится в контролируемой таблице. Статусы «Открыт врачом» и server_at нельзя прислать от астронавта. Клиент не может редактировать audit или receipt.

На клиенте только SUPABASE_URL и publishable key. Secret/service_role исключительно в серверном окружении. Не хранить секреты в VITE_*. Логи исключают access/refresh token, медицинские payload, email и тексты комментариев. Использовать request_id и коды ошибок.

Медицинский API не кэшируется Service Worker. Кэш оболочки и справочников отделён от данных. Не использовать dangerouslySetInnerHTML для пользовательского текста; markdown комментариев не поддерживается. CSP и зависимости проверяются перед демонстрацией. Сервер ограничивает размер payload (например 256 KB на операцию), длины строк и допустимые enum.

Приватность P0 демонстрирует разграничение доступа в приложении и API. IndexedDB без дополнительного шифрования не защищает от владельца устройства, вредоносного ПО и доступа через DevTools. UI-блокировка не называется шифрованием. Использование реальных медицинских данных требует отдельной модели угроз, локального шифрования, политики устройств, retention, юридической и медицинской проверки; это не обещание MVP.

## 21. Демонстрационные данные и необычная подача

### 21.1. Синтетическая миссия

Seed создаёт миссию ORBIT-DEMO-01, длительность 180 дней, режим extended; дата старта задаётся относительно выбранной даты репетиции. Синтетические профили: Mira-01 (астронавт, персональные вопросы включены), Alex-02 (астронавт, выключены), Flight-Doc (врач, назначен обоим). P1: Commander-01, Admin-01. Пароли не в репозитории; аккаунты создаются seed-скриптом из переменных окружения. Локальный набор и серверный набор имеют общий demo_dataset_id.

На каждого астронавта 14 дней синтетической истории: неодинаковые интервалы, один пропущенный день, ручные измерения с unknown quality, несколько явно симулированных пригодных измерений, одна неудачная попытка. У Mira есть одна чувствительная запись только локально и другая с разрешённой передачей. Все числа сконструированы для демонстрации интерфейса, не выдаются за экспериментальные результаты.

Seed не создаёт события «Открыт врачом» или «Доставлен текущий отчёт» для будущего сценария. Исторические fixtures допустимы только с меткой seed_history. Каждый запуск выступления создаёт новые ID; история прошлой репетиции не маскируется под новую передачу.

### 21.2. Экран ведущего /demo/control

Доступ только demo-организатору, не подменяет роли в Supabase. Панель содержит:

- Название набора и версия сценария — read-only.
- «Проверить готовность»: локальный origin, наличие справочников, состояние очереди, реальное соединение, устройство, доступ наземной панели.
- «Выбрать симуляцию сигнала»: стабильный / контакт потерян / поток остановлен; только для simulator-adapter.
- «Приостановить передачу в приложении»: инженерный тест, всегда баннер «Передача приостановлена для теста». Это не называется отключением интернета.
- «Начать новую демонстрацию»: создаёт новый синтетический набор через служебный процесс; не удаляет реальные/посторонние данные. Если очередь не пуста — предупреждение и запрет автоматического сброса.
- «Открыть панель врача»: URL, но без автоматического входа от чужой роли.
- «Проверки сценария»: список фактически выполненных этапов, вычисляемый по журналу, без кнопки «считать пройденным».

Перед живым выступлением панель закрывается. Нет скрытых таймеров, которые автоматически рисуют receipt. Системный Wi-Fi отключается вручную ведущим, поскольку веб-страница не должна обещать управление сетью ОС.

### 21.4. Отличительные элементы продукта

1. «Паспорт измерения»: по клику на значение открываются источник, время, алгоритм качества и ограничения. Это реальная карточка, не декоративный бейдж.
2. «Путь записи»: единая лента от локального сохранения до просмотра врачом. Не смешивает физическую связь с фактом прочтения.
3. «Предпросмотр приватности»: перед отправкой пациент видит ровно тот состав, который будет доступен врачу; отдельно указано, что командир не получает медицинское содержимое.
4. «Почему показана подсказка»: входные данные и версия правила доступны из интерфейса. Формулировки короткие, без вымышленного AI-confidence.
5. «Проверяемая автономность»: страницу можно обновить после отключения интернета, не потеряв запись.

Не добавлять LLM-чат ради впечатления. В P0 генерация отчёта шаблонная и полностью офлайн. Если позже появляется ИИ, его роль, источники и поведение при отсутствии сети специфицируются отдельно.

### 21.5. Резервный план

Если сеть не восстановилась: показывается реальное состояние pending; ведущий объясняет, что локальная часть завершена. Допускается отдельно включить подписанную видеозапись ранее проверенной доставки. Видео не называется live.

Если USB не работает: переключение на ручной ввод или simulator с явной подписью, без подделки device_id и source. Если локальное хранилище не работает, не показывать ложный успех: открыть резервную подготовленную среду/видео. Демо-набор не содержит данных членов команды без их согласия.

## 22. Нефункциональные требования

### 22.1. Производительность

Целевые, подлежащие измерению показатели: на ноутбуке выступления локальное сохранение ≤500 мс для 95% из 100 последовательных записей размером до 20 KB; открытие подготовленной Today ≤2 секунд; график 1000 точек без заметной блокировки ввода; реакция на отсутствие пакетов прибора ≤2,5 секунды. Это критерии приёмки, а не уже достигнутые результаты.

На заведомо исправной сети ручной запуск синхронизации одной записи должен завершаться без лишнего ожидания backoff; время передачи фиксируется, но не обещается жёсткое значение независимо от Supabase/интернета. Главная не ждёт сетевых запросов для отображения локальной истории.

### 22.2. Доступность

Все основные сценарии доступны с клавиатуры. Видимый focus; порядок Tab соответствует визуальному. Нажимаемые области не меньше 44×44 px для основных действий. Контраст текста целевой WCAG AA; проверить автоматикой и вручную. Графики имеют текстовое представление данных. prefers-reduced-motion отключает необязательную анимацию. Состояния успеха/ошибки различаются текстом и иконкой.

### 22.3. Надёжность

Сбой сети не очищает форму. Перезапуск вкладки не теряет committed-записи. Миграции IndexedDB транзакционны и версионированы; при несовместимой версии журнал не сбрасывается автоматически. Новая сборка PWA не активируется посреди несохранённой формы; баннер «Доступно обновление» с действием после сохранения. Старая версия schema принимается сервером на оговорённый переходный период, иначе queued-данные блокируются с объяснением, а не удаляются.

Хранилище браузера может быть очищено пользователем или ОС. Для демо запросить persistent storage, проверить результат, но не обещать абсолютную сохранность. Подготовка показывает, получено ли разрешение. Локальные резервные копии синтетического набора проверяются до выступления.

### 22.4. Наблюдаемость

Локальный технический журнал: timestamp, component, event_code, operation_id, retry_count, duration_ms. В серверном логе аналогично request_id и код результата. Медицинский текст и токены не логируются. Кнопка «Экспорт технического отчёта» формирует JSON без медицинских payload и без секретов; пользователь видит состав перед экспортом. Бортовой медицинский audit не считается защищённым от изменения владельцем устройства; серверный audit защищён правами БД.

### 22.5. Реалистичные ограничения прототипа

Не поддерживаются гарантированная доставка при закрытом браузере, первое открытие без предварительной подготовки, клиническое использование недорогого датчика, автоматическая классификация срочности, защита от администратора ОС, полноценная медицинская электронная подпись, офлайн-работа врача с реальными данными. Эти ограничения доступны в /evidence и README; не скрывать их от жюри, если задан прямой вопрос.

## 23. Полные пользовательские сценарии

### S01. Первый запуск

Организатор создаёт пользователя и назначение → астронавт входит онлайн → проверяет профиль → выбирает персональные вопросы и обмен → загружает набор → видит успешные проверки → открывает Today. Если нет назначения, локальный журнал допускается после подготовки, но отправка отчёта недоступна с понятной причиной.

### S02. Ежедневная запись без прибора

Today → «Заполнить» → ответы → «Нет симптомов» → персональный раздел заполнить/пропустить → «Продолжить без измерений» → проверка → сохранить → открыть запись. Неизмеренный пульс остаётся отсутствующим, не нулевым. Отсутствие устройства не блокирует основной продукт.

### S03. Изменение самочувствия в тот же день

Today → «Добавить запись» → тип «Изменение самочувствия» → симптом и его влияние → запрос внимания врача → сохранить → подготовить отчёт. Утренняя запись остаётся; временная последовательность видна в истории.

### S04. Чувствительная часть только локально

Включить персональные вопросы → заполнить → выбрать «Только на этом устройстве» → сохранить при включённом общем обмене → синхронизировать → врач видит общую запись; запрос чувствительной части API возвращает отказ/отсутствие. В отчёте нельзя случайно включить локальную часть одной общей галочкой без нового явного разрешения.

### S05. Разрешённая чувствительная часть

Пациент выбирает назначенного врача → подтверждает передачу конкретной части → согласие синхронизируется → bundle принят → врач открывает отдельный раздел → доступ фиксируется. Командир и администратор приложения не могут получить содержимое прямым запросом.

### S06. Потеря сети во время отправки

Запись сохранена → RPC отправлен → сеть пропала до ответа → UI остаётся «Передача не подтверждена» → после восстановления worker повторяет тот же operation_id/hash → сервер возвращает исходную квитанцию, если успел принять → дубликата нет. Отчёт на Земле может появиться раньше, чем борт получит подтверждение; UI допускает это.

### S07. Истёкший вход

После подготовки истёк JWT → пользователь офлайн сохраняет новые записи → при связи refresh не удался → queued остаётся blocked_auth → повторный вход тем же пользователем → отправка продолжается. Вход другим пользователем не присваивает ему очередь; предлагается выйти/войти владельцем или отдельно очистить подготовленное устройство после сохранности данных.

### S08. Плохой сигнал

Подключение → ожидание контакта → сбор → потеря контакта/разрыв → invalid → повторить → пригодный результат → сохранить → прикрепить к записи. Невалидная попытка не участвует в медиане и не создаёт «опасный пульс».

### S09. Исправление отправленного

Открыть доставленную запись → «Дополнить / исправить» → причина → сохранить новую ревизию → новый отчёт/дополнение. Врач может открыть предыдущую версию; прошлый snapshot и квитанция не переписываются.

### S10. Отзыв назначения / согласия

Врач имел доступ → администратор отзывает назначение или пациент согласие → сервер закрывает дальнейшее чтение → активная панель очищает недоступный раздел при следующей проверке → борт после pull обновляет назначение. Предыдущие выгрузки не считаются отозванными. Offline-отзыв отображается как ожидающий, не как уже выполненный на сервере.

### S11. Ответ врача

Врач открывает отчёт → вводит уточнение → предпросмотр → отправить → борт получает при связи → карточка «Новое сообщение» → астронавт открывает и нажимает «Прочитано» → подтверждение доставляется отдельно. Врач видит различие server_saved/device_received/patient_read.

### S12. Смена часового пояса

В профиле меняется зона → время отображается в новой зоне → recorded_at и local_date исходного самоотчёта не изменяются → отчёт показывает UTC и понятную локальную подпись. Порядок событий не меняется из-за форматирования.

## 25. Последовательность реализации

### Этап 1. Контракты и данные

Создать TypeScript-типы и схемы payload, enums, SQL-миграции, RLS и seed. Проверить два аккаунта и запрет чужого доступа до наполнения интерфейса. Зафиксировать schema_version=1 и allowlist RPC. Результат: одну запись можно безопасно принять и прочитать разрешённым врачом.

### Этап 2. Локальный журнал

Сделать repository IndexedDB, подготовку устройства, черновик, форму общего самочувствия, локальную историю. Проверить reload без интернета. Результат: реальный вертикальный офлайн-сценарий без красивых графиков.

### Этап 3. Доставка

Добавить outbox, идемпотентный submit_operation, квитанции, 401/403/retry, получение ответов, экран sync. Провести A19–A29. Только после этого статусы доставки выводятся на Today.

### Этап 4. Персонализация и отчёты

Встроить репродуктивный раздел, отдельные таблицы/согласия, предпросмотр приватности, report snapshots, панель врача. Проверить A12–A18, A30–A35. Отключение раздела не должно ломать обычный сценарий.

### Этап 5. Представление и объяснимость

Добавить графики с источниками, «Почему?», evidence, визуальную систему, RU/EN, доступность. Провести пользовательские проверки и исправить найденные затруднения. Не создавать украшения до готовности основных действий.

### Этап 6. Дополнительная демонстрация

Если P0 принят, подключить USB-датчик и P1-командира; при нехватке времени оставить ручной ввод/явную симуляцию. Проверить источники и ограничения на каждом экране. Записать резервное видео работающего сценария.

### Этап 7. Репетиция

Два устройства, production build, отдельный demo Supabase, фиксированный localhost origin. Проверить права, часы, память, очередь, сетевой маршрут, аппаратный кабель. Провести полный сценарий два раза без редактирования БД во время выступления. После репетиции создать свежий набор, не подделывать квитанции.

## 28. Итоговые условия готовности

Прототип готов к заявленному выступлению, если пользователь на подготовленном ноутбуке может отключить интернет, обновить страницу, заполнить и сохранить запись, снова обновить страницу, увидеть сохранённые значения, восстановить связь, получить квитанцию и увидеть тот же отчёт на устройстве врача. Назначенный врач получает только разрешённые данные; посторонний пользователь не может прочитать их через API. Отсутствие измерения, плохой сигнал, устаревшая сессия и отзыв доступа не превращаются в ложные успешные состояния.

Любая заявляемая дополнительная функция должна иметь собственный пройденный сценарий. Необычность презентации строится на наблюдаемой работе системы при ограничениях, а не на скрытом воспроизведении заранее подготовленных ответов.
