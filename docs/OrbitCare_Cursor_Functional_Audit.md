### Источник и приоритет требований

Основа — OrbitCare_TZ_React_Supabase_v1.md от 13.11.2026. Последующие решения пользователя имеют приоритет:
- frontend React, backend Python, PostgreSQL; старые упоминания Supabase/RPC/Edge Functions заменяются эквивалентными серверными операциями;
- в первой версии нет назначения препаратов, выбора лекарственных схем, расчёта дозировок и автоматических диагнозов;
- общий раздел врача называется «План наблюдения», тип «Препарат» исключён;
- репродуктивное здоровье встроено в добровольный персональный раздел самочувствия;
- измерения ESP32 + MAX30102 демонстрационные, не клинические.

Уровни аудита:
- CORE/P0: исходный обязательный сценарий астронавт → локальная запись → доставка → назначенный врач → ответ.
- ADMIN/P1: создание миссий, приглашения, управление составом и назначением врача через UI; в исходном P0 это seed/служебный скрипт.
- PLAN/дополнение: структурированный план наблюдения без лекарств, согласованный после исходного ТЗ.
- DEVICE/P1: USB ESP32; становится обязательным для обещанной аппаратной демонстрации.
- COMMAND/P1: командир и добровольно опубликованные операционные статусы.
- NEXT: другие функции P1/P2, не блокирующие CORE.

Проверить всё описанное, но вынести вердикты отдельно для каждого уровня. Не объявлять CORE проваленным только из-за отсутствия интерфейса администратора или плана наблюдения. Вместе с тем общий сценарий «создать миссию через UI» не считать пройденным, если она создана только seed-скриптом.

## 1. Основные сущности и правила

Различать:
- пользователь: идентификатор авторизации и учётная запись;
- профиль: отображаемое имя, позывной и разрешённые личные настройки;
- миссия: организационный контекст;
- участие в миссии: пользователь + mission_id + роль + статус;
- назначение врача: связь врач–пациент в конкретной миссии с периодом действия;
- план наблюдения: задания врача пациенту; НЕ назначение врача на пациента;
- самоотчёт: запись астронавта и её неизменяемые ревизии;
- измерение: собственный ID, источник, время, качество;
- отчёт: неизменяемый снимок выбранных версий;
- ответ врача: отдельное сообщение со статусами доставки и прочтения;
- согласие: отдельное разрешение на чувствительные сведения;
- операция синхронизации: отдельный idempotency key и серверная квитанция.

Во всех медицинских сущностях проверять принадлежность владельцу и миссии. Роль врача без активного назначения не даёт доступ ко всему экипажу. Членство в миссии также не означает доступ к медицине других участников.

Для первой реализации достаточно одной активной миссии у астронавта и одного активного ответственного врача в её рамках. Это уточнение сценария, не требование NASA. Если реализованы несколько врачей/миссий, проверить явный выбор контекста, однозначного получателя и отсутствие смешивания данных; не требовать упрощения работающей более широкой модели.

## 3. Администратор: создание миссии (ADMIN/P1)

Вход администратора → «Миссии» → «Создать миссию».

| Поле | Обязательно | Валидация и поведение |
|---|---|---|
| Название | Да | 3–80 символов после trim |
| Код | Да | 3–20, латинские буквы/цифры/дефис; нормализация регистра и уникальность на сервере |
| Начало | Да | Дата и время; интерфейс явно показывает зону, хранение UTC |
| Окончание | Да | Строго позже начала |
| Режим | Да | short / extended; выбор явный, не по произвольному числу дней |
| Часовой пояс | Да | Валидная IANA-зона, по умолчанию UTC |
| Порядок обращения за помощью | Нет | До 2000 символов, обычный текст |
| Статус | Системный | При создании draft; пользователь не подменяет его произвольной строкой |

Кнопки: «Отмена» и «Создать миссию». Ошибка показывается у поля, ввод остаётся. Повторный клик не создаёт вторую миссию. После успешного серверного сохранения открывается карточка с вкладками «Обзор», «Участники», «Врачи», «Настройки», «Технический журнал».

Статусы draft → active → completed → archived — новое уточнение жизненного цикла:
- draft: организационная настройка, приглашения и подготовка устройств разрешены;
- active: основной сбор записей и обмен;
- completed: новые обычные самоотчёты в этой миссии не создаются; разрешены досылка ранее сохранённого, ответы, исправления с историей, закрытие начатых заданий;
- archived: просмотр в пределах текущих прав; позднюю синхронизацию не удалять — показать конфликт состояния и сохранить локальные данные.
Изменение статуса только администратором, с подтверждением и аудитом. Даты сами по себе не удаляют/закрывают миссию. До архивирования показывать предупреждение, что сервер не знает обо всех локальных очередях. Возврат completed → active допускается отдельным действием с причиной; из archived — явно восстановить в completed перед дальнейшими изменениями.

Если в репозитории другая модель статусов, описать её и соответствие бизнес-сценарию. Не скрывать это различие автоматическим переименованием.

Перед «Активировать» проверить: корректные даты, минимум один активный астронавт, у каждого активный ответственный врач. Не требовать подготовки устройства как серверного факта, если heartbeat отсутствует. Позволить подготовить устройство в draft. Перед завершением показать активные планы и недоставленные серверу неизвестны по определению; не заявлять «всё синхронизировано» без доказательств.

В режиме short история по умолчанию 7 дней; extended — 30. Права и состав персональных вопросов не зависят от длительности.

## 4. Администратор: пользователи и участие (ADMIN/P1)

«Участники» → «Добавить» → «Пригласить нового» либо «Добавить существующего».

| Поле | Обязательно | Правило |
|---|---|---|
| Email | Для нового | Формат email, trim, до 254; не создавать второй аккаунт для того же нормализованного адреса |
| Отображаемое имя | Да | 1–100 |
| Позывной | Для участника экипажа | 2–20; уникален внутри миссии; не использовать как секрет/ID авторизации |
| Роль | Да | Астронавт / врач / командир из разрешённых администратору |
| Миссия | Да | В карточке миссии предзаполнена; сервер проверяет доступ |
| Пользователь | Для существующего | Выбор существующего аккаунта, вместо повторного приглашения |

Администратор системы создаётся bootstrap-процедурой; форма приглашения в миссию не должна позволять незаметно выдать глобальную роль администратора. Возраст, пол, цикл и симптомы администратор в приглашении не заполняет.

Состояния: приглашён → активен → деактивирован; отдельно истёкшее приглашение. Приглашение имеет ограниченный срок и однократный токен. «Повторить приглашение» не создаёт второй аккаунт; старый токен отзывается. «Отозвать приглашение» блокирует активацию по ссылке. Если почта в demo не настроена, показать реальный альтернативный способ активации тестового аккаунта, а не «Письмо отправлено».

Принятие: переход по ссылке → проверка токена → создание пароля/подключение существующей авторизации → вход. Пароль и его политика должны соответствовать фактическому auth-провайдеру; интерфейс и backend используют одно правило. При самостоятельном хранении паролей проверить безопасный password hashing, отсутствие plaintext в БД/логах. Саморегистрация вне приглашения выключена.

Администратор видит статус приглашения, роль, миссию, доступность аккаунта. Не видит пароль и медицинские подробности. Деактивация сохраняет историю и аудит, запрещает новые серверные операции пользователя. Непереданные локальные записи сохраняются; интерфейс объясняет отказ, не стирает их.

Для CORE без ADMIN подготовить те же сущности seed-скриптом. Секреты тестовых аккаунтов не коммитить и не печатать в отчёте.

## 5. Назначение врача пациенту (CORE данные, ADMIN интерфейс)

«Врачи» → «Назначить врача».

Поля: активный врач, активный астронавт той же миссии, начало действия, необязательное окончание строго после начала. Пациент и врач не могут быть одной и той же учётной записью в тестовом сценарии. Запретить перекрывающиеся назначения при модели одного ответственного врача.

«Подтвердить» создаёт связь и событие аудита. Членство врача в миссии без этой связи не раскрывает медицинские сведения. Будущее назначение не даёт доступ до начала; истёкшее — после окончания.

«Отозвать» требует причину 1–300 символов и подтверждение. Следующий серверный запрос старого врача отклоняется; открытый экран обновляет права при фокусе и не реже 60 секунд. Уже прочитанные сведения невозможно технически «забыть».

Смена врача — одно проверяемое действие с закрытием старого назначения и открытием нового, без случайного перекрытия. В данном сценарии согласие на чувствительные данные привязано к конкретному назначению: новому врачу требуется новое разрешение. Это уточнение приватности; проверить фактическую модель и отметить расхождение.

Отчёт, адресованный старому врачу, не перенаправляется молча. Если назначение изменилось до доставки — понятная ошибка и создание нового отчёта новому врачу после предпросмотра. Старый snapshot и очередь не уничтожаются. Общая передаваемая история доступна новому врачу в рамках активного назначения; чувствительная — только после отдельного разрешения. Доступ к ранее отправленным частным ответам также перепроверяется по действующим правам.

Если врача нет, астронавт может сохранять локальный дневник, но отправка отчёта недоступна. Отсутствие врача отличается от сетевой ошибки. Подготовка устройства должна честно показать отсутствие назначения; основной демонстрационный обмен не считается готовым.

## 6. Первый запуск каждого пользователя

Астронавт: приглашение/тестовый аккаунт → вход онлайн → подготовка устройства → профиль и приватность → «Сегодня».
Врач: вход онлайн → «Входящие» → только назначенные пациенты; мастер бортовой офлайн-подготовки не появляется.
Администратор: вход → «Миссии»; медицинские маршруты запрещены.
Командир: вход → «Экипаж»; видит только добровольно опубликованные операционные статусы.
Пользователь без активной роли: экран «Доступ не назначен», выход/контакт администратора; не пустая медицинская панель и не автоматическая роль астронавта.

Далее перечислены точные поля и состояния из исходного ТЗ. Указанные пути — ориентиры для сопоставления, не обязательные имена URL. P1 внутри блоков сохраняет исходный приоритет. Слово «назначение» в старых блоках про доступ означает назначение врача на пациента, а не лекарство.

## 7. Экран входа и подготовка устройства — P0

### 7.1. /login

Левая часть: название, фраза «Наблюдение за здоровьем экипажа при ограниченной связи», три коротких пояснения. Правая: карточка входа.

| Элемент | Тип и правила | Действие |
|---|---|---|
| Электронная почта | email, обязательно, trim, до 254 символов | Проверка формата |
| Пароль | password, обязательно; не изменять пробелы автоматически | Кнопка «Показать пароль» переключает маску |
| Войти | Primary | серверная авторизация; при успехе маршрут по назначенной роли |
| Забыли пароль? | Ссылка | Онлайн-запрос восстановления; одинаковый ответ независимо от существования email |
| Язык | RU/EN | Меняет интерфейс |
| Открыть подготовленный журнал | Только при наличии локального профиля | Офлайн-режим существующего устройства без изменения облачных прав |

Саморегистрация отключена. Ошибка входа: «Не удалось войти. Проверьте данные или соединение». Сетевую ошибку можно уточнить без раскрытия аккаунта. В P0 локальный журнал содержит только синтетические данные; локальный вход не считается защищённой медицинской аутентификацией. До реального использования нужна отдельная защита устройства и ключей. Нельзя просто кешировать JWT и считать это бессрочным разрешением на сервер.

### 7.2. /prepare

Мастер из трёх шагов. Один бортовой origin хранит одного астронавта. Для другого пользователя требуется синхронизация/экспорт очереди и очистка локального профиля.

Шаг 1 «Проверьте профиль»: позывной, имя, миссия, назначенный врач, период миссии — read-only из сервера. «Это мои данные» обязательно. «Сообщить об ошибке» показывает контакт организатора без отправки произвольного письма.

Шаг 2 «Настройте журнал»: язык; часовой пояс отображения; предпочтительное время ежедневного напоминания HH:MM; персональные вопросы on/off; режим чувствительных данных; чекбокс «Передавать завершённые общие записи назначенному врачу». В демо передача общих записей нужна для основного сценария, но пользователь видит последствия выбора. Напоминание P0 работает только при открытом приложении; не обещать фоновые push.

Шаг 3 «Подготовьте устройство»: список проверок «Интерфейс доступен», «Локальное хранилище доступно», «Профиль загружен», «Справочники загружены», «История загружена», «Правила загружены», «Назначение врача проверено». Для PWA дополнительно «Офлайн-ресурсы сохранены». Каждая строка имеет статус и кнопку «Повторить» при ошибке. Кнопка «Загрузить и проверить» выполняет подготовку; «Начать работу» активна после обязательных проверок. Если сервер недоступен при первой подготовке, полноценного запуска нет.

При недоступной IndexedDB: «На этом устройстве невозможно надёжно сохранить журнал»; завершение записи запрещено, ввод можно скопировать из черновика. При малом объёме хранилища предупреждение; очередь не удаляется автоматически.

## 8. «Сегодня» — /onboard/today, P0

Порядок сверху вниз:

1. Заголовок «Сегодня», дата, подпись «Ваш журнал на этот день».
2. Главная карточка «Самочувствие»: ещё не заполнено / черновик / завершено. Основная кнопка соответственно «Заполнить», «Продолжить», «Открыть запись». В завершённом состоянии вторичная «Добавить запись» для изменения самочувствия в тот же день; новое событие не перезаписывает утреннее.
3. Карточка «Последнее измерение»: пульс или «Измерений пока нет», единица, время, источник, качество. Кнопка «Измерить» ведёт на измерения. Если значение устарело по настройке интерфейса, текст «Последнее измерение X назад», не «Текущий пульс».
4. Карточка «На что обратить внимание»: максимум 3 нерешённых события качества/полноты/изменений. Каждое содержит заголовок, объяснение, время, «Почему?» и конкретное действие. При пустом состоянии «Новых подсказок нет»; не «Вы здоровы».
5. Карточка «Связь с врачом»: последний ответ, время его получения; кнопка «Открыть». Если ответа нет: «Ответов пока нет». Отдельно доставка: N операций ожидают связи.
6. Лента последних 5 событий: запись, измерение, сформирован отчёт, подтверждена доставка, просмотр врачом. Личные чувствительные подробности в заголовки общей ленты не выводятся.

Кнопка «Связаться с медиком» доступна постоянно. Открывает окно с выбором «Подготовить сообщение» или «Показать бортовой порядок обращения». Второе открывает заранее заданный миссией текст контакта/действий без диагностических инструкций. При отсутствии такого материала: «Порядок обращения для этой миссии не настроен». Приложение не обещает экстренную доставку сообщения без связи.

## 9. Форма самочувствия — /onboard/checkin/new, P0

Пять логических шагов: «Общее» → «Симптомы» → «Персональные вопросы» (если включены) → «Измерения» → «Проверка». Верхний stepper показывает фактическое число шагов. Слева/сверху прогресс, справа компактная подсказка о локальном сохранении. Внизу закреплены «Назад», «Сохранить черновик и выйти», «Продолжить». На первом шаге «Назад» заменяется «Отмена» с сохранением черновика. Перед уходом с несохранённым вводом предупреждение.

Форма привязана к конкретному draft_id. Повторное открытие восстанавливает тот же черновик. На борту один активный черновик самочувствия; «Добавить запись» при существующем черновике предлагает продолжить или удалить его после подтверждения.

### 9.2. Шаг «Симптомы»

Первый вопрос: «Есть ли симптомы, которые вы хотите отметить?» — «Нет», «Да», «Не хочу отвечать». Если «Нет» или пропуск, список скрывается; ранее введённые значения при переключении не стираются без предупреждения «Удалить ранее добавленные симптомы из этой записи?».

При «Да»: кнопки выбора «Головная боль», «Головокружение», «Тошнота», «Дискомфорт в животе», «Боль в мышцах/суставах», «Ощущение сердцебиения», «Другое». Список — словарь версии, а не диагностическая классификация.

Каждый выбранный симптом создаёт отдельную раскрытую карточку:

| Поле / кнопка | Правила |
|---|---|
| Название | Из словаря; для «Другое» текст 2–80 символов, обязательно |
| Выраженность | 0–10, обязательна или «Не могу оценить» |
| Когда началось | «Сейчас», «Сегодня раньше», «Более суток назад», «Не знаю» |

Ответ «Да» создаёт запрос просмотра, но не медицинский диагноз и не сигнал гарантированного экстренного реагирования. Под кнопкой: «Без связи запрос будет доставлен позже. При необходимости немедленной помощи используйте бортовой порядок обращения».

### 9.4. Шаг «Измерения»

Показывает все доступные локальные измерения за выбранный день: вид, число/единица, время, источник, качество. Checkbox «Прикрепить» доступен только для завершённого измерения; плохое качество можно приложить как неудачную попытку, но не использовать как числовое основание подсказки.

Кнопки «Новое измерение» открывает встроенную панель страницы измерений с возвратом в форму; «Ввести вручную» открывает ручную форму; «Продолжить без измерений» допустима всегда. Пустая карточка: «Измерения необязательны. Запись самочувствия можно сохранить отдельно».

Нельзя автоматически прикреплять старый пульс как текущий. Каждая связь содержит measurement_id; исходное измерение не копируется с потерей происхождения.

### 9.5. Шаг «Проверка и сохранение»

Блоки: время и тип записи; общее состояние; симптомы; прикреплённые измерения; свёрнутая чувствительная часть с явным получателем; запрос врачу. Рядом с каждым «Изменить» возвращает на нужный шаг без потери остальных данных.

Три строки доставки: «Общая часть: назначенному врачу / только устройство», «Персональный раздел: …», «Связь: доступна / отсутствует». Если общая передача выключена, пользователь может включить её для записи; чувствительная отправка требует общего медицинского обмена, иначе объяснение и выбор сохранить только локально.

Кнопка «Сохранить запись» выполняет одну локальную транзакцию: неизменяемая ревизия + связи измерений + разрешённые outbox-операции + журнал локального события. Только после commit показывать успех. Черновик помечается завершённым. Облачный сбой не отменяет локальный успех.

Экран результата: «Запись сохранена на устройстве», время, «Ожидает передачи» либо «Получена сервером», кнопки «Открыть запись», «Подготовить отчёт», «На сегодня». Если пользователь выбрал только локальное хранение, текст «Хранится только на этом устройстве» вместо ошибки синхронизации.

### 9.6. Просмотр и исправление записи

Заголовок, дата, версия, способ ввода, статус доставки. Секции соответствуют проверке. Кнопки «Дополнить / исправить», «Создать отчёт», «Показать версии». Исправление создаёт новую ревизию с обязательной причиной до 300 символов, не меняет исходник. Уже отправленный отчёт остаётся неизменным; рядом появляется «Есть более новая версия записи». Новая ревизия не передаёт ранее локальную чувствительную часть без нового разрешения.

Завершённые записи не удаляются обычной кнопкой. Действие «Пометить ошибочной» требует причины, создаёт событие аннулирования; исходные данные сохраняются в истории и исключаются из тенденций. Реальное удаление персональных данных — отдельная процедура вне P0, не имитируется скрытием карточки.

## 10. Измерения — P0 ручной ввод, P1 USB

Верх: название «Измерения», вкладки «Новое»/«История». Карточка способа: «Вручную», «USB-датчик», «Симулятор» (только demo). Видимый источник обязателен в результатах, графиках и отчётах.

### 10.1. Ручное измерение

| Поле | Правило |
|---|---|
| Показатель | Пульс / Температура тела / SpO₂; обязательно |
| Значение | Пульс 20–250 целое уд/мин; температура 30–45,0 °C шаг 0,1; SpO₂ 50–100 % целое |
| Время | Обязательно, по умолчанию сейчас; ограничение будущего +5 минут |
| Контекст | В покое / После нагрузки / Другое / Не указан |
| Прибор/способ | Необязательный текст до 100 символов; «Не указан» по умолчанию |
| Примечание | До 300 символов |
| Сохранить измерение | Локальное сохранение с quality=unknown, source=manual |

Диапазоны — техническая защита от опечаток для демо, не диапазоны нормы и не критерии здоровья. При выходе: «Значение вне поддерживаемого диапазона ввода. Проверьте единицы; исходное наблюдение можно описать в комментарии». Не обрезать число до ближайшей границы. Ручной ввод не получает статус «Подтверждено датчиком».

### 10.2. USB-панель

Поддерживаемая конфигурация выступления: проверенный desktop Chrome/Edge, secure context localhost/HTTPS, ESP32 по USB. При отсутствии navigator.serial вместо ошибки: «USB-подключение недоступно в этом браузере. Доступен ручной ввод». Разрешение порта запрашивается только по нажатию.

Карточка устройства: имя, firmware_version, device_id, соединение, последний пакет, источник «USB». Кнопки «Подключить», «Отключить», «Начать измерение», «Отменить». «Начать» активна при подключённом совместимом устройстве и отсутствии другого измерения.

Состояния: disconnected → connected → waiting_contact → collecting → evaluating → result_valid / result_invalid. Разрыв на любом активном этапе ведёт в interrupted, без фиктивного результата. «Повторить» создаёт новый attempt_id, предыдущая попытка сохраняется как техническое событие.

Во время сбора: инструкция «Положите палец и держите его неподвижно», таймер 30 секунд, индикатор контакта, график исходного сигнала с подписью «Оптический сигнал PPG» (не ЭКГ), текст качества. Кнопка «Сохранить результат» появляется после завершения и ручного подтверждения. Во время потока ничего не отправляется на сервер.

Контракт JSON Lines: protocol_version, device_id, firmware_version, session_id, seq, uptime_ms, contact_detected, raw_ir, raw_red (если доступен), hr_bpm nullable, quality_flags[]. Один JSON на строку, UTF-8, максимальная длина строки 4 KB. Часы события добавляет браузер; uptime не является UTC. Неизвестная версия протокола блокирует начало и показывает понятную ошибку.

Новый seq принимается один раз в пределах session_id. Неполная строка буферизуется до newline. Некорректная строка игнорируется с техническим счётчиком; после 5 последовательных ошибок сессия прерывается. Если 2 секунды нет пакетов, график останавливается и появляется «Нет новых данных»; прежний пульс не показывается как текущий.

Алгоритм качества Q1: без контакта, с флагом насыщения, с разрывом >2 секунд или недостаточным числом пригодных оценок — invalid/insufficient. Для демо пригодный результат требует минимум 20 секунд контакта в 30-секундном окне, минимум 10 ненулевых пригодных оценок HR, отсутствия saturation; итог — медиана пригодных оценок. Пороговые параметры и версия алгоритма сохраняются. Эти критерии проверяют полноту и грубые артефакты, не доказывают медицинскую точность. Если устройство не умеет выдавать нужные признаки, quality=unknown; не рисовать «Высокое качество».

Сдвиг пальца не обязан всегда обнаруживаться; на презентации нельзя обещать распознавание любого движения. Сценарий качества заранее проверяют на реальном приборе. MAX30102 в первой аппаратной версии используется для пульса/PPG; SpO₂ с него не демонстрируется как достоверное измерение без отдельной валидации.

Карточка результата: значение, единица, время, метод, quality, объяснение, «Сохранить», «Повторить», «Закрыть без сохранения». При invalid числовой итог скрыт, остаётся «Не удалось получить пригодное измерение»; «Сохранить попытку» фиксирует неудачу без числового значения. Если подключён прибор другого добровольца, измерение остаётся в отдельном демонстрационном профиле, не смешивается с историей астронавта.

Симулятор имеет постоянную подпись «СИМУЛЯЦИЯ». Профили «Стабильный сигнал», «Потеря контакта», «Разрыв потока»; результат source=simulated. Он тестирует UI и очередь, не считается тестом аппаратного качества.

## 11. История и тенденции — P0

Экран /onboard/history: сверху диапазон «7 дней / 30 дней / Весь период / Выбрать даты»; поля «С» и «По» в пользовательской зоне; кнопка «Применить». Начало не позже конца. Дефолт 7 дней. Фильтр типа «Все / Самочувствие / Измерения / Отчёты / Ответы». Фильтр источника «Все / Ручной / Устройство / Симуляция».

Первый блок — графики сна, усталости и пульса, каждый отдельной карточкой. Ось X — время; Y с единицей и явным диапазоном. Не соединять линией большие пропуски. Невалидные попытки показаны отдельными значками под графиком и не участвуют в среднем. Ручные значения отличаются маркером от приборных, симуляция — подписью и штриховым стилем. Tooltip содержит точное время, значение, источник, качество и ссылку на исходник. Нет общего нормализованного графика, смешивающего несопоставимые единицы.

Ниже список событий по убыванию времени: дата, тип, короткое содержание, источник, локальный/доставленный статус. Нажатие открывает запись. «Загрузить ещё» подгружает следующие 25 локальных событий. «Поиск в комментариях» не входит в P0, чтобы не создавать лишнюю индексацию чувствительного текста.

Личная тенденция P0 — описательная статистика. Для выбранного показателя сравнивается последнее пригодное наблюдение с медианой предыдущих 7 суток при наличии минимум 5 наблюдений на минимум 3 разных днях. Отбор учитывает одинаковые единицы; приборный и ручной источники не объединяются автоматически. Выборка и контекст показываются в «Как рассчитано». Если данных мало: «Недостаточно истории для сравнения». Надпись «Личная медиана» не заменяется словом «Норма».

Для сна берётся последняя неаннулированная ежедневная запись на дату, чтобы дополнительные записи не увеличивали вес дня. Пропуски не заменяются нулём. Для пульса сравниваются только сохранённые пригодные значения в покое из сопоставимого источника. Нельзя выводить риск заболевания из тренда. Пороговая подсветка медицинских рисков отсутствует в P0.

Чувствительная история открывается отдельной вкладкой «Персональные записи» только у владельца или разрешённого врача; не попадает в общий tooltip. Сводный календарь цикла P1 показывает только введённые даты и события, без предсказания.

## 12. Подсказки и объяснения — P0

Название раздела «Наблюдения и качество данных», а не «Диагнозы». Три типа: действие пользователя, техническое качество, описательное изменение. Не вводить процент уверенности, если он не получен из валидированной модели.

| rule_id | Условие | Текст | Действие |
|---|---|---|---|
| DATA_CONTACT_LOST_V1 | Попытка завершена без контакта/с прерыванием | «Измерение не завершено» + фактическая причина | «Повторить измерение» |
| DATA_NO_CURRENT_V1 | В записи нет прикреплённого измерения | «Запись сохранена без измерений» | «Добавить измерение»; информационный, не тревога |
| SELF_REVIEW_REQUEST_V1 | Пользователь явно попросил внимание врача | «Вы запросили просмотр записи» | «Подготовить отчёт» |
| SYNC_AUTH_REQUIRED_V1 | Сервер вернул отказ из-за истёкшей сессии после попытки refresh | «Для отправки нужен повторный вход» | «Войти» |
| HISTORY_CHANGE_V1 | Доступно сравнение по правилам раздела 11 | «Показатель отличается от вашей предыдущей медианы на X» | «Посмотреть историю» |

HISTORY_CHANGE не создаёт клинической срочности; по умолчанию показывается только в истории. На главную выносится по явному действию «Закрепить наблюдение». В P0 нет автоматической красной тревоги на основании общего самочувствия, выделений или изменения пульса.

Карточка объяснения: заголовок; конкретные входные данные со ссылками; timestamp вычисления; версия правила; результат; ограничение; источник, если он обосновывает контекст. Если правило инженерное, указать «Правило прототипа». Нельзя прикреплять NASA-источник так, будто NASA утвердило наши числовые пороги.

«Отметить просмотренным» записывает acknowledge события, но не исправляет неудачное измерение и не закрывает запрос врачу. «Скрыть с главной» — только предпочтение отображения. Медицинский статус из этого не выводится.

## 13. Отчёты и обмен с врачом — P0

### 13.1. Создание отчёта

Вход из записи, истории или списка отчётов. Модальное окно/отдельная страница:

| Поле | Правило |
|---|---|
| Название | До 120 символов, по умолчанию «Самочувствие · дата» |
| Период | Сегодня / 7 дней / Выбрать даты; не включает будущее |
| Записи | Список с checkbox; минимум одна запись или одно измерение |
| Получатель | Назначенный врач, read-only; при отсутствии назначения отправка запрещена, локальный черновик допустим |
| Причина | Плановый отчёт / Прошу посмотреть / Ответ на запрос врача |
| Сообщение | Необязательно, до 2000 символов |
| Общая часть | Список включаемых типов и количество записей |
| Персональный раздел | По умолчанию выключен; включение только для записей с разрешённой передачей и отдельным подтверждением |
| Предпросмотр | Открывает точный состав будущего отчёта |
| Сохранить и поставить в очередь | Создаёт неизменяемый snapshot и outbox |

Предпросмотр показывает получателя, выбранные версии, время среза, ограничения качества. Пользователь может открыть каждое исходное событие. Приложение не дописывает медицинские заключения. Сводка генерируется детерминированным шаблоном, без облачного LLM: «За период заполнено N записей. Запрос просмотра: да/нет. Прикреплено N измерений, из них N с неизвестным качеством». Чувствительные поля не попадают в общую сводку.

Отчёт состоит из общей и отдельной чувствительной частей. Права доступа не задаются одним JSON-флагом внутри общей строки. Каждая часть имеет отдельный hash; общий hash и доступный командиру/администратору статус не раскрывают содержимое чувствительной части. Hash — контроль целостности передачи, не цифровая подпись и не доказательство медицинской достоверности.

### 13.2. Статусы

Три независимых поля:

1. Локальная готовность: draft / finalized / superseded.
2. Доставка: local_only / queued / sending / accepted / failed / blocked_auth / conflict.
3. Работа врача: not_opened / opened / replied.

«Получен сервером» присваивается только по ответу API с receipt_id и accepted_at. «Открыт врачом» — только после успешной загрузки отчёта врачом и отдельного серверного acknowledge. «Ответ получен» — после загрузки ответа на борт. Realtime-событие и галочка в интерфейсе не подменяют receipt. Если сервер принял, а клиент потерял ответ, повторная отправка возвращает тот же receipt.

### 13.3. Список и карточка

/onboard/reports: фильтры «Все / Ожидают передачи / Получены сервером / С ответом»; карточки: название, период, получатель, статусы доставки и просмотра, последняя активность. «Создать отчёт» вверху справа. Нажатие открывает карточку.

Карточка отчёта: название и ID; лента «Сохранён → Получен сервером → Открыт врачом → Ответ доставлен» с реальными временами, незавершённые этапы серые; вкладки «Содержание», «Ответы», «Доставка». Кнопки «Повторить отправку» при retryable-ошибке, «Создать дополнение», «Печатная версия». Отправленный snapshot не редактируется; дополнение — новый отчёт со ссылкой на предыдущий.

«Печатная версия» открывает локальную print-friendly страницу с датой, версиями, источниками, качеством и пометкой демо. Перед включением персональных разделов отдельное подтверждение. Файлы автоматически в серверное файловое хранилище не отправляются. На общедоступном компьютере экспорт реальных данных не предполагается.

## 14. Панель врача — P0

### 14.1. /ground/inbox

Врач работает онлайн. При потере сети баннер «Нет связи. Показан срез на HH:MM»; уже загруженное остаётся только в памяти с видимой давностью. Новое отправление ответа и подтверждение просмотра недоступны; введённый ответ сохраняется в памяти текущей вкладки с предупреждением, что закрытие потеряет черновик. Медицинский offline-кэш врача в P0 не реализуется.

Верх: фильтр миссии из назначений, «Обновить», время успешного обновления. Три счётчика: «Новые отчёты», «Запрошен просмотр», «Ответ отправлен». Это рабочая очередь, не автоматическая медицинская сортировка по тяжести.

Фильтры: пациент по позывному/имени, период, «Все / Не открыты / Открыты / С ответом», «С запросом просмотра». Список строк: позывной; название отчёта; период; requested_review; время поступления; статус. Сортировка: запросы просмотра выше, затем дата поступления; подпись «Порядок по запросам пользователей, не клинический триаж». Нажатие ведёт на отчёт.

Справа необязательная панель выбранного пациента: позывной, миссия, дата последней доставленной записи, кнопка «Карточка пациента». Нет «живого состояния», если последняя запись устарела.

### 14.2. /ground/crew/:id

Шапка: имя, позывной, миссия, активность назначения. Вкладки «Обзор», «История», «Отчёты», «Персональные данные» (только при разрешении). Обзор показывает последние доставленные сведения и возраст каждого источника. Отдельно «На устройстве могут быть ещё неотправленные записи» — сервер не знает их содержания и количества без отдельного технического heartbeat; в P0 число не выдумывается.

P1 блок «Параметры наблюдения»: врач задаёт персональный reference note и ориентиры только как документированную настройку после медицинского согласования. P0 отображает лишь описательную медиану, не редактируемые клинические пороги.

### 14.3. /ground/reports/:id

Слева содержание отчёта, справа карточка ответа. Сверху receipt, версия, получено_at и статус целостности. После успешной полной загрузки общей части клиент вызывает mark_report_opened; открытие чувствительной части фиксируется отдельно и не считается состоявшимся при отказе доступа.

Карточка ответа имеет заголовок «Ответ члену экипажа»:

| Поле / кнопка | Правило |
|---|---|
| Получатель | Автор отчёта, read-only |
| Тип ответа | Подтверждение получения / Уточняющий вопрос / Комментарий |
| Текст | Обязательно 1–3000 символов |
| Связанная запись | Необязательный выбор из включённых в отчёт |
| Видимость | Только пациент и назначенный врач; если ответ касается чувствительных данных — обязательная отметка «Чувствительная часть» |
| Предпросмотр | Показывает адресата и текст |
| Отправить ответ | Онлайн API, блокировка повторного клика; после commit статус «Сохранён на сервере, ожидается получение устройством» |

Приложение не генерирует врачебный совет. Для демонстрации используется нейтральный заранее согласованный текст: «Отчёт получил. Уточните, когда началось изменение самочувствия». Доставка ответа на борт подтверждается отдельным receipt; серверная запись ответа не означает, что астронавт его прочитал. Астронавт нажимает «Прочитано» — явное подтверждение.

Врач не редактирует исходные ответы астронавта. Ошибочный ответ исправляется новым комментарием со ссылкой на предыдущий, не удаляется бесследно. В P0 нет прикрепления произвольных файлов и лекарственных назначений.

## 15. Профиль, настройки, миссии

### 15.1. Профиль астронавта — P0

Секции «Основное», «Настройки журнала», «Приватность», «Устройство».

| Поле | Тип / редактирование |
|---|---|
| Имя и позывной | Read-only в P0; администратор задаёт при подготовке |
| Миссия, дата старта/окончания | Read-only |
| Назначенный врач | Read-only; активность назначения из последнего среза |
| Возраст | Необязательное целое 18–100 для синтетического взрослого профиля; дата рождения в P0 не собирается |
| Пол для медицинского контекста | Женский / Мужской / Интерсекс / Не указывать; необязательно |
| Рост / масса | P1; в P0 не собирать без использования |
| Язык | RU/EN |
| Часовой пояс | Поиск IANA-зоны; значение по умолчанию UTC для миссии |
| Время напоминания | HH:MM; переключатель вкл/выкл; работает при открытом приложении |
| Персональные вопросы | Вкл/выкл с пояснением последствий |
| Контекст цикла | Те же варианты, что в форме; необязательно; не выводить в обычной карточке профиля |
| Обмен общими завершёнными записями | Вкл/выкл; отключение влияет на новые записи, не удаляет отправленные |
| Разрешение на чувствительные сведения | Только локально / Передавать врачу; изменение фиксируется событием |

«Сохранить настройки» сохраняет локально и ставит разрешённые операции в очередь. Онлайн-изменения назначения врача не инициируются астронавтом. Смена часового пояса меняет отображение, но не UTC-время старых событий и не их изначальную дату самоотчёта.

«Очистить устройство»: окно показывает число неотправленных операций. При ненулевом числе действие заблокировано до синхронизации либо подтверждённого экспорта синтетической резервной копии P0. Подтверждение фразой «ОЧИСТИТЬ»; очищается только локальный профиль, не серверные данные. «Выйти» очищает токены и память; отдельно предлагается оставить подготовленный синтетический журнал или очистить его. На реальных данных такая политика требует переработки.

Локальная резервная копия демо: JSON с version, dataset_id, profile_id, данными и outbox; предупреждение «Файл содержит демонстрационные персональные сведения». Импорт только в demo, с проверкой версии и совпадения владельца; сначала предпросмотр количества событий, затем транзакция. Не считать незашифрованный экспорт пригодным для реальной медицины.

### 15.2. Короткие и длительные миссии

Оболочка и безопасность одинаковы. У миссии явная настройка short/extended, а не клиническая классификация по произвольному порогу дней. В short дефолт истории 7 дней и акцент на текущей записи; в extended — 30 дней, регулярность заполнения и тенденции. Набор полей не расширяется ежедневно автоматически. Персональные вопросы и права одинаковы в обоих режимах. Длительная миссия не включает дополнительные диагнозы.

### 15.3. Командир — P1

На /command только карточки экипажа: позывной, добровольно опубликованное «Доступен / Нужна корректировка нагрузки / Не публиковать», время публикации, срок актуальности, техническая доступность канала при наличии данных. По истечении срока «Статус устарел». «Нужна корректировка» не сопровождается причиной.

Астронавт публикует статус отдельной кнопкой «Операционный статус» на Today. Форма: значение, срок актуальности до 24 часов, предпросмотр «Это увидит командир», «Опубликовать». Никакого автоматического вывода из менструации, усталости или пульса. Отзыв создаёт tombstone и синхронизируется при связи. Командир не может открыть медицинскую карточку по клику.

### 15.4. Администратор — P1

Вкладки «Миссии», «Участники», «Назначения», «Технический журнал». Создать миссию: название 3–80, code 3–20 латиница/цифры/дефис, start_at UTC, end_at > start_at, mode short/extended, default_timezone, текст порядка обращения до 2000, сохранение. Все даты валидируются сервером.

Пригласить пользователя: email, отображаемое имя 1–100, позывной 2–20, роль из разрешённых, миссия. Секретный вызов через Python API с проверкой роли администратора; клиент не содержит привилегированного серверного ключа. Пользователь не может назначить себе роль через metadata.

Назначить врача: выбор активного врача, пациента, дата начала, дата окончания nullable; подтвердить. Отозвать: причина 1–300, предупреждение о прекращении серверного доступа. Ни один администратор не открывает медицинский payload. Служебный лог показывает operation_id, код ошибки, время, компонент, но не комментарии, симптомы и токены.

## 16. Экран связи — /onboard/sync, P0

Вверху три независимые карточки: «Доступность сервера», «Авторизация», «Очередь операций». В каждой текст, время проверки, действие. Кнопка «Проверить связь» выполняет короткий запрос. «Синхронизировать сейчас» запускает worker, но не создаёт копии операций. «Войти повторно» открывает Auth; после входа совпадение user_id обязательно, иначе очередь остаётся заблокированной.

Таблица очереди: тип записи, дата создания, состояние, попытки, последняя ошибка, следующее повторение. Чувствительные значения и даже детальные названия симптомов здесь не выводятся. Для чувствительной операции название «Защищённая медицинская часть», доступ только владельцу. Кнопки строки: «Повторить» для временной ошибки; «Посмотреть причину»; «Разрешить конфликт» если нужно. Кнопки «Пометить доставленным» нет.

Состояния outbox: pending, sending, retry_wait, accepted, blocked_auth, blocked_permission, validation_error, conflict. Успешные операции можно скрыть фильтром, но история квитанций сохраняется.

Тексты:

- Нет сети: «Сохранение на устройстве работает. Передача продолжится после восстановления связи».
- 401 после refresh: «Нужен повторный вход. Записи сохранены».
- 403: «Сервер не разрешил передачу. Проверьте назначение и доступ».
- 422: «Часть записи не прошла проверку. Откройте подробности».
- Квота/429: «Сервер временно ограничил запросы. Повтор запланирован».
- Ошибка хранилища: «Не удалось сохранить на устройстве. Не закрывайте форму».
- Конфликт: «На сервере есть другая версия. Исходные записи сохранены».


## 17. План наблюдения — согласованное дополнение PLAN

Это расширение после исходного ТЗ. Проверять отдельно от CORE. Раздел доступен назначенному врачу и конкретному пациенту. В нём НЕТ типа «Препарат», дозировки, пути введения, схемы лекарственного приёма или кнопки назначения терапии. Поле следования ранее назначенной схеме в самоотчёте остаётся добровольным контекстом и не создаёт лекарственного назначения.

### 17.1. Создание врачом

Карточка пациента → «План наблюдения» → «Добавить задание». Врач работает онлайн.

| Поле | Обязательность и поведение |
|---|---|
| Пациент | Обязательно, предзаполнен, только из активного назначения |
| Миссия | Автоматически из пациента/контекста |
| Тип | Измерение / обследование / дневник симптомов / повторная консультация / немедикаментозная рекомендация |
| Название | Обязательно, 3–120 символов |
| Цель/основание | Необязательно, до 500, не автоматическое заключение |
| Инструкция | Обязательно, 1–2000; обычный текст, без HTML |
| Начало | Обязательно, дата/время с зоной |
| Расписание | Разово / ежедневно; недельные сложные расписания вне первой реализации |
| Срок | Для разового задания — due_at; для ежедневного — время HH:MM и дата окончания |
| Часовой пояс расписания | Обязательно; по умолчанию зона миссии |
| Пересмотр | Необязательная дата/время, не раньше начала |
| Связанный отчёт/запись | Необязательно; только доступные этого пациента |
| Видимость | Общая медицинская / чувствительная; командир и администратор не видят обе |
| Приоритет задачи | Обычный / просит внимания; не автоматический медицинский триаж |

Поля по типу:
- Измерение: показатель «Пульс / температура / SpO₂»; контекст «В покое / после нагрузки / не задан»; доступный способ «Ручной ввод / USB-пульс, если реализован». MAX30102 не становится автоматически источником температуры или достоверной SpO₂.
- Обследование: название обследования; место/исполнитель необязательно; результат в первой версии — статус и текстовый комментарий, без произвольных файлов и автоматического заключения.
- Дневник симптомов: словарь наблюдаемых симптомов или текст до 300; переход к обычной форме самочувствия, без второй несовместимой формы.
- Консультация: время, канал связи и инструкция подключения; ссылка разрешена только безопасного протокола HTTPS, вывод как ссылка без выполнения кода.
- Немедикаментозная рекомендация: инструкция и срок; никаких автоматически сгенерированных врачебных советов.

Для чувствительной задачи обязательно действующее разрешение. Если его нет, создание блокируется с объяснением; нельзя сохранить чувствительное содержание в общем комментарии. Отметка видимости должна распространяться на текст, напоминания, результаты выполнения и экспорт.

Кнопки «Сохранить черновик», «Предпросмотр», «Опубликовать», «Отмена». Черновик виден только автору; до публикации пациент ничего не получает. Предпросмотр показывает адресата, поля, расписание и видимость. После публикации фиксируются автор, версия, серверное время и аудит. Это подтверждённая учётной записью операция, не юридически значимая ЭЦП.

### 17.2. Доставка и выполнение

Три независимых измерения состояния:
- план: draft / active / completed / cancelled / superseded;
- доставка конкретной версии: server_saved / device_received / patient_acknowledged;
- экземпляр задания: pending / done / skipped / unable; overdue вычисляется из срока, если результата нет.

После публикации нельзя сразу писать «Пациент ознакомлен». Доставка на борт подтверждается после устойчивого локального сохранения, ознакомление — явной кнопкой. Для ежедневной задачи создавать отдельные экземпляры на даты с уникальным occurrence_id; поздняя синхронизация не создаёт дубликаты. Фиксировать timezone расписания; смена зоны отображения не переносит назначенное время молча.

У астронавта «Мой план»: карточки на сегодня, просроченные, будущие, завершённые. Карточка: название, врач, срок/время, инструкция, статус доставки/ознакомления. Чувствительная карточка не раскрывает текст в общих уведомлениях.

Действия:
- «Ознакомлен» — отдельное событие, не выполнение.
- «Выполнить измерение» — открывает ввод/прибор; после сохранения предлагает прикрепить конкретный measurement_id.
- «Заполнить дневник» — создаёт/открывает самоотчёт, после завершения связывает checkin_id и ревизию.
- «Отметить выполненным» — для обследования, консультации или рекомендации; фактическое время обязательно, комментарий до 1000 необязательно.
- «Пропустить» — причина из списка «Забыл / Нет возможности / Другое / Не хочу указывать»; текст до 500 необязателен.
- «Не могу выполнить» — комментарий до 1000 и предложение связаться с врачом; без автоматической смены лечения.
- «Задать вопрос» — сообщение, связанное с заданием, с той же видимостью.

Нельзя закрыть задание измерения только открытием страницы. Для успешного выполнения нужна связанная сохранённая пригодная запись; невалидную попытку можно приложить с результатом unable. Ручное качество unknown не приравнивать к invalid: ручное измерение допустимо, источник остаётся виден. Для задания дневника требуется завершённая запись, не черновик.

Пациент может отметить выполнение офлайн: локальная транзакция + очередь; врач увидит после доставки. Новое задание, ещё не полученное устройством, офлайн не появляется «из воздуха». Напоминания при закрытом приложении не обещаются в первой версии.

### 17.3. Изменение, отмена и конфликты

Врач меняет активное задание через «Изменить» с обязательной причиной до 300. Создаётся новая версия; выполненные экземпляры и старые инструкции сохраняются. Изменение не действует задним числом. Пациент видит «План обновлён» после получения и подтверждает новую версию.

«Отменить» требует причину; новые экземпляры не создаются, история остаётся. Если пациент офлайн выполнил старую версию после серверной отмены, не терять событие: сохранить время, старую версию и отметку «Выполнено по ранее полученному плану; требуется просмотр». Не показывать это как выполнение актуальной версии.

При отзыве назначения врача старый врач теряет возможность редактировать задания. Уже полученный пациентом план остаётся с предупреждением об изменении сопровождения. Новый врач после получения полномочий явно пересматривает/переиздаёт план; авторство старых записей не заменяется.

### 17.4. Критерии приёмки PLAN

PLAN-01: врач без назначения не создаёт задание прямым API-запросом.
PLAN-02: тип «Препарат» и связанные структурированные поля отсутствуют и отклоняются сервером.
PLAN-03: черновик не виден пациенту и не создаёт напоминаний.
PLAN-04: публикация не означает доставку или ознакомление.
PLAN-05: однократное подтверждение не создаёт дубликаты при повторе сети.
PLAN-06: выполнение офлайн сохраняется после reload, затем появляется у врача.
PLAN-07: изменение создаёт новую версию, старое выполнение остаётся привязанным к старой.
PLAN-08: отмена при офлайн-клиенте не уничтожает поздний факт выполнения.
PLAN-09: sensitive-план/результат не попадает в общую историю, уведомления и API без права.
PLAN-10: просрочка не превращается автоматически в «Выполнено» или медицинскую тревогу.
PLAN-11: пациент не редактирует врача, инструкцию или срок через подмену payload.
PLAN-12: завершение задания одной миссии не прикрепляет запись другой миссии/пользователя.

## 18. Backend, хранение и синхронизация: что проверять в Python/PostgreSQL

Это замена технологических требований Supabase из исходного ТЗ, с сохранением поведения.

- Backend сам устанавливает author_id/subject_id из аутентификации и проверяет права на указанный объект. Клиентские role, mission_id и doctor_id не доверенные.
- Доступ к БД у браузера отсутствует. Если Data API всё же открыт, нужны отдельные политики ограничения; обычная проверка FastAPI не защищает обходной публичный API.
- PostgreSQL RLS может быть дополнительным слоем. Отсутствие именно Supabase RLS не ошибка; отсутствие эффективной серверной изоляции — ошибка.
- Миграции определяют внешние ключи, уникальности, допустимые статусы и индексы. Таблицы могут называться иначе; составить карту соответствия сущностям.
- Чувствительные данные отделены от общих в хранении, сериализации, отчётах, ответах и правах. Общий endpoint не возвращает скрытый объект sensitive с CSS-маскировкой.
- Времена UTC; локальная дата самоотчёта и зона — отдельные значения. Авторское время отличается от времени приёма сервером.
- Локальный журнал астронавта хранится в IndexedDB, не только React-state. Черновики и неподтверждённые измерения не отправляются.
- Локальная транзакция одновременно сохраняет финальную ревизию, связи и разрешённые outbox-операции. При провале транзакции не показывать успех.
- operation_id + hash и уникальное ограничение обеспечивают идемпотентность. Повтор того же ID и содержимого возвращает ту же квитанцию; тот же ID с другим содержимым — конфликт.
- Сервер принимает bundle общей и разрешённой чувствительной частей атомарно. При отказе чувствительной части не молча отправлять общую как будто весь bundle принят.
- Зависимости: исходные записи/измерения → отчёт → связанные подтверждения. Ошибка одной независимой операции не останавливает всю очередь.
- Конфликт parent_revision сохраняет обе версии и требует явного разрешения; нет silent last-write-wins для медицинских данных.
- Повторная передача после потери ответа сервера не дублирует запись.
- 401: попытка обновить сессию, затем blocked_auth и повторный вход тем же владельцем.
- 403: blocked_permission, объяснение; не бесконечные немедленные повторы.
- 422: validation_error, указание поля/кода, локальный ввод остаётся.
- 429/временная 5xx/обрыв: retry с задержкой, ограничением и учётом Retry-After.
- Факт navigator.onLine не равен доступности API. Упавший сервер при работающем интернете отображается корректно.
- Две вкладки не отправляют независимо разрушающие операции; блокировка worker + серверная идемпотентность.
- Pull использует устойчивый курсор без пропуска конкурентно зафиксированных событий; WebSocket/SSE — ускорение, повторное чтение обязательно.
- Маркеры accepted, opened, replied, read имеют отдельные серверные события; клиент не может присвоить их себе.
- Логи содержат request_id/operation_id и коды, без медицинских текстов, паролей, токенов.
- В demo используются синтетические данные. Нешифрованный IndexedDB не представляется защищённым медицинским хранилищем.

## 19. Контрольный набор пользователей и данных

Создать ТОЛЬКО в изолированном demo/test, без реальной почтовой рассылки:
- admin: организационные операции без медицинского доступа;
- patient_A: астронавт миссии M1, персональные вопросы включены;
- patient_B: астронавт M1, персональные вопросы выключены;

- doctor_C: назначен C в M2;
- commander_M1;
- anon.

M1: активная, extended. M2: активная, short. Дополнительно draft-миссия для проверки создания. Даты задавать относительно тестового времени, чтобы проверки не сломались из-за календаря.

Данные A: 7 дней синтетических записей, минимум 5 пригодных наблюдений в покое на 3 разных днях одного источника; отдельное ручное, невалидное и simulated измерение; одна local_only чувствительная запись; одна разрешённая чувствительная запись; один отчёт без чувствительной части; одно сообщение врача. Нельзя смешивать реальный замер добровольца с вымышленным астронавтом.

## 20. Сквозные сценарии аудита

Для каждого: предусловия → действия → ожидаемое UI → ожидаемое БД/сеть → фактическое доказательство.

### FLOW-01. От пустой системы до готового экипажа (ADMIN)
1. Войти admin; создать draft M1 с корректными полями.
2. Попробовать неверный конец и дублирующийся код; получить ошибки без потери ввода.
3. Пригласить врача и A/B; принять приглашения в тестовом канале.
4. Назначить doctor_A обоим; проверить отсутствие доступа doctor_B.
5. Подготовить устройство A онлайн.
6. Активировать миссию; проверить доступ A к «Сегодня» и doctor_A к своей очереди.
Ожидается: все сущности связаны, никто не назначил себе роль, admin не читает медицину. При отсутствии ADMIN повторить функционально через seed и отдельно отметить, что UI-сценарий отсутствует.

### FLOW-02. Обычный дневник без персональных вопросов (CORE)
1. Войти B, пройти подготовку, оставить персональные вопросы выключенными.
2. «Заполнить»: ежедневная, самочувствие «Хорошее», сон 7,5, качество 4, усталость 2, стресс 3, спокойное состояние.
3. Симптомы «Нет», просмотр врача «Нет».
4. Продолжить без измерений; на проверке общая часть врачу.
5. Сохранить, перезагрузить страницу.
Ожидается: шаг персональных вопросов отсутствует; значения сохранены; нет утверждения «здоров»; отсутствие пульса не блокирует запись.

### FLOW-03. Приватная чувствительная запись (CORE)
1. A включает персональные вопросы; заполняет общую часть.
2. Указывает мажущие выделения, необязательные ответы и чувствительный комментарий.
3. Выбирает «Только это устройство»; общую часть разрешает врачу.
4. Сохраняет и синхронизирует.
Ожидается: сервер получает только общую часть. Чувствительный текст отсутствует в сетевых payload, ответах API, логах и общей сводке. Doctor_A не видит содержание или скрытый запрос обсуждения чувствительной части.

### FLOW-04. Разрешённая чувствительная запись (CORE)
1. A явно разрешает передачу персонального раздела действующему doctor_A.
2. На проверке видит точного получателя и состав.
3. Сохраняет, формирует отчёт с отдельным включением раздела и синхронизирует.
4. doctor_A открывает общую и персональную части.
Ожидается: две области доступа и отдельная фиксация открытия; doctor_B, B, commander и admin получают отказ при прямом запросе.

### FLOW-05. Реальный офлайн-сценарий (CORE)
1. Production build на фиксированном localhost origin; первая подготовка онлайн.
2. Отключить внешнюю сеть, оставив локальный HTTP-сервер.
3. Reload → форма → частичный ввод → reload → продолжить.
4. Сохранить итоговую запись и ручное измерение, сформировать отчёт.
5. Закрыть и открыть вкладку.
6. Восстановить связь; дождаться настоящей квитанции.
7. На другом устройстве doctor_A открывает тот же отчёт.
Ожидается: данные переживают перезапуск; до связи «на устройстве/в очереди», после квитанции «получен сервером», после открытия — отдельный статус. Хеш/версии совпадают, повторных строк нет.

### FLOW-06. Ответ врача (CORE)
1. doctor_A открывает отчёт; тип «Уточняющий вопрос», текст «Уточните, когда началось изменение самочувствия».
2. Предпросмотр → отправить.
3. A офлайн: врач видит только server_saved.
4. A выходит онлайн, получает ответ: device_received.
5. A нажимает «Прочитано»: patient_read после доставки подтверждения.
Ожидается: три разных этапа; врач не меняет исходный самоотчёт; чувствительный ответ наследует ограничения.

### FLOW-07. План наблюдения (PLAN)
1. doctor_A создаёт ежедневное задание «Измерить пульс в покое», задаёт срок и время; сохраняет черновик.
2. A не видит черновик; врач публикует.
3. A получает, подтверждает ознакомление, отключает сеть.
4. Сохраняет ручное измерение, связывает его с экземпляром задания.
5. Reload → результат на месте; восстановление связи → врач видит выполнение и источник.
6. Повторить с «Не могу выполнить» и комментарием.
Ожидается: открытие страницы не выполняет задачу; нет дубликатов; состояния ознакомления/выполнения/доставки независимы.

### FLOW-08. Изменение и отзыв плана (PLAN)
1. A получил v1 и ушёл офлайн.
2. Врач публикует v2 или отменяет задание.
3. A выполняет v1 и синхронизируется.
Ожидается: факт не потерян, явно привязан к v1; не закрывает новое задание ошибочно; есть отметка расхождения.

### FLOW-09. Ошибка измерения (DEVICE)
1. Подключить реальный ESP32; разрешить USB; проверить device_id и версию протокола.
2. Начать сбор; разорвать контакт/USB.
3. Не получать фиктивное число; сохранить неудачную попытку или повторить.
4. Выполнить успешный сбор и явно сохранить.
Ожидается: поток PPG не называется ЭКГ, старые числа не «живые», invalid не участвует в медиане, simulator всегда помечен. Ручной ввод доступен при отказе USB.

### FLOW-10. Исправление доставленной записи (CORE)
1. A открывает отправленную запись → «Исправить», вводит причину и новое значение.
2. Сохраняет новую ревизию; создаёт дополнение.
Ожидается: старый snapshot отчёта не изменён; врач видит версии; новая редакция не раскрывает ранее локальный персональный раздел.

### FLOW-11. Отзыв согласия и смена врача (CORE/ADMIN)
1. Doctor_A имеет доступ к разрешённому разделу.
2. A отзывает согласие онлайн; повторить прямой API-запрос.
3. Повторить отзыв офлайн: отображается ожидание, серверное ограничение не заявлено раньше доставки.
4. Admin заменяет doctor_A на doctor_B.
Ожидается: старый врач теряет доступ; новый не получает автоматически чувствительное разрешение; подготовленные старому врачу отчёты не перенаправляются скрытно.

### FLOW-12. Командир (COMMAND)
1. A отдельно публикует «Нужна корректировка нагрузки», срок 2 часа.
2. Командир видит статус без причины и медицинских ссылок.
3. Изменить чувствительный самоотчёт: командир не получает новых сведений.
4. После срока показать «Устарел»; проверить отзыв и задержку офлайн.
Ожидается: статус не вычисляется из цикла/пульса; прямой медицинский API запрещён.

### FLOW-13. Повторные запросы и конфликт (CORE)
1. Двойной клик на сохранении.
2. Потеря ответа после серверного commit.
3. Повтор operation_id с тем же и затем другим payload.
4. Две вкладки; несовпадающий parent_revision.
Ожидается: один логический результат, прежняя квитанция при повторе; конфликт при другом содержимом; обе версии сохранены.

### FLOW-14. Истёкшая сессия и другой пользователь (CORE)
1. У A подготовлен журнал и pending-очередь; токен истёк.
2. Сохранить офлайн ещё запись.
3. Восстановить связь, refresh неуспешен.
4. Попробовать войти B, затем A.
Ожидается: очередь не присваивается B; A после входа продолжает отправку; ни одна запись не потеряна.

### FLOW-15. Завершение миссии (ADMIN)
1. A имеет сохранённую до завершения локальную запись.
2. Admin переводит M1 в completed.
3. A синхронизирует старую запись.
4. Проверить создание новой обычной записи, исправление старой, ответ врача.
Ожидается: старое не потеряно; новые обычные записи заблокированы после получения состояния; допустимые действия работают. Созданное на устаревшем офлайн-срезе сохраняется локально и получает объяснимый конфликт, а не удаление.

## 21. Матрица условных полей: обязательные ветки

| Условие | Показывать/разрешать | Скрывать/блокировать |
|---|---|---|
| Медицинский пол «Женский», персональные вопросы ещё не включены | Предложение включить | Автоматический сбор чувствительных данных |
| Любой пол, настройка включена | Добровольный персональный шаг | Обязательность ответов из-за пола |
| Настройка выключена | Общие шаги; доступ к своей истории по отдельному входу | Новый персональный шаг |
| «Пропустить раздел» | Переход дальше | Заключение «симптомов нет» |
| Выделений нет/не уверен/отказ отвечать | Остальные добровольные вопросы | Поле выраженности выделений |
| Есть выделения | Необязательная выраженность | Автоматический расчёт кровопотери |
| Контекст «назначенная схема подавления» | Следование ранее назначенной схеме | Дозировки и совет компенсировать пропуск |
| Контекст изменён на другой | Остальные вопросы | Отправку скрытого старого ответа о схеме без подтверждения |
| Симптомы «Да» | Карточки симптомов | Сохранение «Другое» без названия |
| Симптомы «Нет» после введённых | Подтверждение удаления карточек | Тихую потерю ввода и отправку скрытых старых симптомов |
| Чувствительная часть local_only | Локальное сохранение | Сеть, сервер, отчёт врачу с этим содержимым |
| Общее медицинское согласие выключено | Локальный журнал; явное включение для записи | Отправку чувствительной части отдельно без общего обмена |
| Нет назначенного врача | Локальный дневник, черновик отчёта | Отправку в неопределённый адрес |
| Врач не в своём назначении | Понятный отказ | Медицинские поля и обход прямым API |
| Врач офлайн | Срез с давностью, черновик ответа в памяти с предупреждением | «Ответ отправлен», серверное подтверждение открытия |
| Астронавт офлайн после подготовки | Дневник, история, сохранение, очередь | Ложные квитанции и новые неполученные планы |
| Первый запуск офлайн | Объяснение необходимости подготовки | Фиктивную готовность устройства |
| Нет пригодного измерения | Сохранение самоотчёта без числа | Ноль вместо отсутствующего значения |
| Нет достаточной истории | «Недостаточно истории» | Выдуманную норму/медиану |
| Задание draft | Редактирование врачом | Видимость пациенту |
| Задание sensitive, разрешение отсутствует | Объяснение ограничения | Публикацию/чтение чувствительного содержания |
| Задание измерения | Показатель, способ, связанное измерение | Тип «Препарат» |
| Задание консультации | Время, канал | Поля дозы и измерения |
| Клиент прислал чужой ID | Отказ всей операции | Частичную привязку чужих данных |

При скрытии полей определить явную политику черновика. Не терять значения без предупреждения; не включать неактуальные скрытые значения в финальный payload. Null, skipped, unknown и реальный 0 должны быть различимы.

## 22. Границы функций и трактовка ошибок

- «Нет данных» не равно «всё в порядке».
- «Сохранено локально» не равно «доставлено врачу».
- «Сервер принял» не равно «открыто врачом».
- «Ответ сохранён» не равно «пациент прочитал».
- «Доступ к персональному разделу скрыт» не равно «API его защищает».
- «Приложение открылось без сети после посещения» не доказывает первый офлайн-запуск.
- «Медиана» не является индивидуальной медицинской нормой.
- MAX30102 не измеряет репродуктивное здоровье; персональные сведения — самоотчёт.
- Демо-режим не может незаметно заменять реальный датчик или квитанции.
- Врачебный комментарий и план наблюдения не должны рекламироваться как лекарственные назначения.
- Кнопка «Подписать» без инфраструктуры подписи не означает ЭЦП.
- Обновление страницы/смена языка/переход назад не сбрасывают форму.
- Вход/выход, удаление локальных данных и деактивация — разные действия.
- Удаление участника из текущего списка не удаляет медицинскую историю.
- Отзыв доступа не отменяет ранее сделанные внешние выгрузки.

## 23. Формат результата Cursor

Сформируй AUDIT_REPORT.md, не редактируя продуктовый код.

1. Фактический стек и команды запуска.
2. Какие части удалось запустить; ограничения окружения.
3. Карта экран → компонент → API → сервис → таблица → проверка доступа.
4. Матрица сценариев FLOW-01…FLOW-15, PLAN-01…PLAN-12 и исходных A01…A50.
5. Матрица условных полей из раздела 21.
6. Серверные проверки роли/назначения/согласия/миссии и попытки обхода.
7. Расхождения со старым ТЗ отдельно от ошибок.
8. Блокеры демонстрации: потеря данных, утечка чужих данных, фиктивная доставка, неработающий основной поток.
9. Минимальный план исправлений в порядке зависимости: права/данные → локальное сохранение → доставка → пользовательские формы → дополнительные сценарии → визуальные детали.
10. Сводка отдельно: CORE; ADMIN; PLAN; DEVICE; COMMAND. Для каждого «Готово / Частично / Не готово / Не проверено», без фиктивных процентов.

Формат строки:
| ID | Уровень | Ожидаемое | Фактическое | Статус | Доказательство | Влияние | Минимальное исправление |

Если тест не запускался, прямо укажи это. Не составляй положительный отчёт только по наличию названий методов или скриншотов.

## Приложение A. Исходный чек-лист A01–A50

Технологические названия приведены к Python API/PostgreSQL. SQL-политики обязательны там, где БД/таблицы доступны напрямую через Data API; в остальных случаях проверяются эффективные серверные права и обходные пути. Под «RPC» исходного ТЗ понимается соответствующая транзакционная операция Python API.
