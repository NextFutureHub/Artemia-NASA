# Artemia / OrbitCare — ТЗ на расширение системы наблюдения за здоровьем
Версия 1.0 · 15.11.2026
Стек: React + TypeScript; Python API; PostgreSQL; локальный журнал IndexedDB.
Рабочее название не влияет на требования.

## 1. Назначение, границы и применение документа

Документ описывает целевое поведение расширенного прототипа: что хранить, на каком экране, кто вводит, когда запрашивать и как доставлять. Это задание для реализации и проверки, не утверждение о готовности текущего кода.

Документ дополняет OrbitCare_Cursor_Functional_Audit.md. При конфликте по новым разделам, периодам записи и единицам использовать уточнения этого документа; требования безопасности, идемпотентности и неизменяемой истории сохраняются. Прежний P0 не становится автоматически неготовым из-за отсутствия новых функций.

Принцип: краткий ежедневный самоотчёт + отдельные записи событий + назначенные по расписанию наблюдения. Не превращать интерфейс в одну обязательную медицинскую анкету на десятки экранов.

Источники NASA подтверждают направления мониторинга и организацию медицинской помощи. Конкретные поля, интервалы, маршруты, enum и шкалы ниже — проектные решения. Нельзя писать «обязательная анкета NASA», «соответствует всем требованиям NASA» или «одобрено NASA».

Нет автоматических диагнозов, определения годности к работе, расчёта доз и назначения лекарств. Режим demo — синтетические профили. Реальные измерения добровольца хранить отдельно от вымышленного астронавта с пометкой демонстрации.

### Приоритеты

- BASE: уже согласованная основа — авторизация, подготовка устройства, дневник, персональный раздел, ручные измерения, история, отчёты, права и доставка.
- EXT-1: питание/жидкость, тренировки, расширенный сон, профиль здоровья, общий план наблюдения.
- EXT-2: обследования, плановые консультации, адаптация/зрение, расширенный контекст миссии.
- ADMIN: управление миссиями, пользователями и врачебными назначениями через UI; seed остаётся допустимым способом запуска BASE.
- DEVICE: отдельная интеграция ESP32; не заменять её неотмеченной симуляцией.
- NEXT: импорт лабораторных файлов, автоматический учёт рациона, телеметрия среды и радиации, клинические правила, реальные медицинские данные.

## 2. Роли

| Роль | Что делает | Что не получает автоматически |
|---|---|---|
| Астронавт | Заполняет свой журнал, сохраняет измерения, выполняет задания, управляет разрешениями | Чужие медицинские данные; изменение инструкции врача |
| Назначенный врач | Просматривает разрешённые данные своих пациентов, создаёт план, ведёт консультации, проверяет результаты | Локальные записи; чувствительные сведения без отдельного разрешения |
| Администратор | Миссии, учётные записи, состав, назначения врачей, организационные настройки | Симптомы, результаты, медицинские комментарии |
| Командир | Отдельно опубликованные операционные статусы своей миссии | Медицинские причины статуса, персональные разделы, показатели здоровья |
| Бортовой медицинский ответственный | В этой версии только контакт в миссии | Никаких медицинских прав без отдельной реализованной роли |

Все права проверяются Python API по текущему пользователю, mission_id, активному назначению и согласию. Изменение роли в браузере не меняет права. Администратор приложения не равен владельцу PostgreSQL.

## 4. Миссия: контекст и жизненный цикл

Миссию создаёт администратор онлайн. Это организационные сведения, а не ежедневный ввод астронавта.

| Поле | Обязательность | Правило |
|---|---|---|
| Название | Да | 3–80 символов |
| Код | Да | 3–20, латиница/цифры/дефис, уникален |
| Тип | Да | Орбитальная / лунная / межпланетная / наземный аналог |
| Начало и окончание | Да | UTC; окончание позже начала |
| Режим | Да | short / extended, явный выбор |
| Зона расписания | Да | IANA, по умолчанию UTC |
| Текущая фаза | Да | Подготовка / полёт / поверхность / возвращение / восстановление |
| Порядок обращения за помощью | Нет | Текст до 2000; при отсутствии явно «Не настроено» |
| Бортовой медицинский контакт | Нет | Имя/роль/канал связи, без выдачи полномочий |
| Ожидаемая задержка связи | Нет | Неотрицательное число секунд; это плановая оценка, не измеренный ping |
| Окна связи | Нет | Список начала/окончания с зоной |
| Оборудование | Нет | Справочник доступных приборов; отсутствие оборудования не означает отсутствие медицинской потребности |

Окна связи не блокируют фактически доступный API. Не считать сетевую задержку временем доставки врачу. Для demo имитация задержки включается отдельно с постоянной подписью «Симуляция связи».

Статус миссии и фаза — разные поля:
- draft: настройка и подготовка;
- active: сбор и обмен;
- completed: новые обычные записи не создаются, ранее сохранённые доставляются, исправления/ответы доступны;
- archived: история по действующим правам; поздняя очередь сохраняется и требует явного разрешения состояния.

Фазы меняются только явным действием с историей. Не определять их автоматически по календарной дате. Для орбитальной миссии «поверхность» может быть неприменима; не требовать прохождения всех фаз. Реабилитационные записи возможны в фазе «восстановление», пока статус active.

«Активировать миссию»: корректные данные, минимум один активный астронавт, каждому назначен ответственный врач. Подготовка устройства возможна в draft. Административное завершение не должно молча отбрасывать локальную очередь.

## 5. Участники и первый запуск

Администратор добавляет существующего пользователя либо приглашает нового: email, отображаемое имя, позывной, роль, миссия. Медицинский пол, анамнез и симптомы через форму приглашения не собираются.

Назначение врача: врач, пациент, миссия, начало, необязательное окончание. Для первой реализации один активный ответственный врач на пациента в миссии. При смене врача старое назначение закрывается; чувствительное разрешение новому врачу запрашивается заново. Уже сформированные отчёты не перенаправляются молча.

Астронавт впервые входит онлайн:
1. Проверяет имя, позывной, миссию, врача и подтверждает профиль.
2. Выбирает язык, зону отображения, metric/us, время напоминания.
3. Настраивает общий обмен и добровольные персональные вопросы.
4. Приложение загружает профиль, миссию, справочники, разрешённую историю, план, правила.
5. Проверяет IndexedDB и доступность оболочки без внешних ресурсов.
6. «Начать работу» открывает «Сегодня» после успешных обязательных проверок.

Ошибка необязательного нового раздела не блокирует локальный дневник: например, недоступный endpoint обследований показывает «Раздел временно недоступен», не ломает сохранение самоотчёта. Ошибка хранилища блокирует обещание успешного локального сохранения.

У врача онлайн-вход ведёт во «Входящие», без мастера подготовки бортового журнала. Один основной локальный профиль на origin. Смена пользователя не присваивает ему чужую очередь.

## 7. Экран «Сегодня»

Показывать:
- миссию, фазу, день миссии, дату/зону;
- ежедневную запись: не заполнена / черновик / завершена;
- задачи на сегодня и просроченные;
- последнее сохранённое измерение с возрастом, источником и качеством;
- следующую консультацию с зоной и каналом;
- последний ответ врача;
- локальную очередь и последний успешный обмен.

Кнопки: «Заполнить», «Продолжить», «Открыть запись», «Добавить событие», «Измерить», «Открыть план», «Связаться с врачом».

Нет показателя «здоровье экипажа 97%», автоматической годности и зелёного «Вы здоровы». Просроченная анкета — организационное событие, не медицинская тревога. Для чувствительной задачи на общей карточке только «Персональное задание», подробности после перехода владельца.

## 8. Ежедневная форма: общие правила

Шаги: Общее → Сон → Питание → Симптомы → Персональные вопросы (если включены) → Измерения → Проверка.

Активность показывается на проверке как связанные записи за период; повторно вводить тренировку не требуется. «Добавить тренировку» открывает отдельную форму с возвратом.

Черновик автоматически сохраняется через 500 мс и при смене шага. Статус сохранения только после транзакции. «Назад», смена языка/единиц и открытие вспомогательной формы не теряют ввод.

Для необязательного раздела доступны «Заполнить» и «Пропустить». Поля без предвыбранного медицинского ответа. Значения 0, null, unknown, skipped и declined различимы. При изменении ответа скрытые неактуальные значения не отправляются; перед удалением уже введённых значений — предупреждение.

Ежедневная запись имеет local_date и report_period. Повтор на ту же дату предлагает открыть/исправить основной отчёт либо создать событие изменения состояния. Не перезаписывать прежнюю запись. Дополнительное событие не увеличивает число суток в статистике.

## 9. Общее самочувствие

| Поле | Обязательность | Условие/значения |
|---|---|---|
| Время наблюдения | Да | По умолчанию сейчас; будущее не более +5 минут |
| Тип | Да | Ежедневная / изменение самочувствия |
| Самочувствие | Да | Очень плохое / плохое / среднее / хорошее / очень хорошее |
| Усталость | Ответ либо отказ | 0–10 / не оценивать |
| Стресс | Ответ либо отказ | 0–10 / не оценивать |
| Эмоциональное состояние | Ответ либо отказ | Спокойное / напряжённое / подавленное / приподнятое / другое / не хочу отвечать |
| Контекст | Нет | После сна / тренировки / EVA / изменения режима / перехода гравитации / другое |
| Комментарий | Нет | До 1000 символов |

У «Другое» контекста/эмоции — необязательный текст до 120. EVA и гравитационные события доступны через «Дополнительный контекст», а не занимают всю ежедневную форму. В наземном аналоге такие события помечаются как аналоговые/симулированные.

Изменение самочувствия открывает короткий путь: общее → симптомы → дополнительные разделы по выбору → проверка. Сон и питание повторно не требуются.

## 10. Сон и восстановление

Период: последние 24 часа относительно времени наблюдения. Этот период виден над формой и сохраняется вместе с записью.

| Поле | Формат | Когда |
|---|---|---|
| Общая продолжительность сна | 0–24 ч, шаг 0,5 / не знаю | Основной вопрос |
| Качество сна | 1–5 / не оценивать | Основной вопрос |
| Сонливость в рабочий период | Не было / небольшая / выраженная / не оценивать | Необязательно |
| Пробуждения | Не было / были / не помню | Необязательно |
| Отклонение от плана | Нет / да / план не задан / не знаю | Необязательно |
| Что мешало | Шум / свет / задачи / дискомфорт / другое | При плохом сне либо раскрытии «Подробнее» |
| Обсудить режим | Да/нет | Необязательно |
| Комментарий | До 500 | Необязательно |

«Подробнее о периодах сна»: список start_at/end_at, основной/дополнительный, оценка «спал» либо «находился в постели». Конец позже начала, пересечение полуночи разрешено; одинаковые интервалы не дублируются. Перекрывающиеся интервалы требуют исправления, не суммируются дважды.

Общая продолжительность и интервалы — альтернативные источники, не слагаемые. Если введены оба, показать расхождение и попросить выбрать основной источник. Интервалы нахождения в постели не преобразовывать в подтверждённое время сна. Детальные интервалы необязательны и могут быть вторым этапом реализации.

Не выводить диагноз бессонницы и не объявлять используемую шкалу валидированным психологическим тестом.

## 11. Питание и жидкость

По умолчанию период совпадает с последними 24 часами ежедневного самоотчёта. Не смешивать «сегодня с полуночи» и «последние 24 часа» в одной агрегированной серии. Допускается изменить период явно; начало раньше конца, конец не позже наблюдения.

| Поле | Варианты | Условие |
|---|---|---|
| Заполнить питание? | Да / пропустить | Всегда |
| Аппетит | Обычный / снижен / повышен / не оценивать | Если заполняет |
| Выполнение плана питания | Полностью / частично / не выполнен / план не задан / не знаю | Если заполняет |
| Пропущенные приёмы | Целое ≥0 / не знаю | При частичном/невыполненном плане |
| Причина | Нет аппетита / тошнота / нет времени / другое / не указывать | При отклонении |
| Учтённая жидкость | Число ≥0 / не отслеживал | Необязательно |
| Полнота учёта жидкости | Полный / частичный / не знаю | Обязательно при числе |
| Комментарий | До 500 | Необязательно |

Жидкость означает сообщённый объём выпитых напитков; не обещать учёт всей воды в пище. 0 — явный ответ, не дефолт. Для API объём в mL, длительность периода и полнота обязательны при наличии числа. Конкретные верхние технические пределы зафиксировать в общей схеме валидации как защиту ввода, не медицинскую норму; не обрезать большие числа автоматически.

Если плана питания нет, интерфейс не придумывает цель и процент выполнения. Предусмотреть ссылку на ранее согласованную инструкцию в плане наблюдения; не разрабатывать меню и подсчёт нутриентов в этом этапе. Ответ «полностью» — самоотчёт, не доказательство достаточного питания.

Не считать калории из аппетита и не диагностировать обезвоживание. Персональные количественные цели добавляются только с автором, датой и источником; по умолчанию отсутствуют.

Масса тела вводится в «Измерениях» по расписанию, не обязательна ежедневно. Указать способ измерения. Для микрогравитации не изображать обычные весы как работающий источник.

## 12. Симптомы, зрение и адаптация

Первый вопрос: «Есть ли симптомы, которые хотите отметить?» — Нет / да / не хочу отвечать. При «Да» минимум одна карточка или возможность вернуться и изменить ответ.

Словарь BASE: головная боль, головокружение, тошнота, дискомфорт в животе, боль в мышцах/суставах, ощущение сердцебиения, другое.
EXT-2: изменение зрения, нарушение равновесия. Не создавать дублирующийся опрос головокружения в другой секции.

Карточка симптома:
- название; для «Другое» 2–80 символов обязательно;
- выраженность 0–10 либо «Не могу оценить»;
- начало: сейчас / ранее сегодня / более суток назад / не знаю;
- течение: постоянное / периодическое / не знаю;
- влияние: не мешает / немного / сильно / не оценивать;
- комментарий до 500;
- удалить из черновика с возможностью отмены.

При «Изменение зрения» показать:
- нечёткость / затруднение чтения / другое / не могу описать;
- один глаз / оба / не могу определить — необязательно;
- контекст появления — необязательно.

Не просить проходить некалиброванный экранный тест остроты зрения. Не выводить «SANS обнаружен» или «SANS исключён». Нормальный ответ не отменяет обследование по плану.

При задаче врача «Отметить изменения зрения» отрицательный ответ является выполненным наблюдением, если запись сохранена; он не означает медицинского заключения.

В конце общей части — «Запросить просмотр врачом?» Да/нет. При офлайн объяснить отложенную доставку и показать миссионный порядок обращения. Не обещать срочную помощь через очередь.

## 13. Персональное здоровье

Включается владельцем отдельно от пола. Женский пол может вызывать предложение включить менструальный раздел, но не автоматический сбор. Для любого пола доступны применимые добровольные разделы.

### Менструальное здоровье

Поля:
- заполнить сегодня: да/пропустить;
- выделения: нет / мажущие / менструальные / другие / не уверена(ен) / не хочу отвечать;
- выраженность: незначительные / умеренные / обильные / не могу оценить — только при наличии;
- ожидаемо ли это: да/нет/не знаю/не хочу отвечать — при наличии;
- дискомфорт или спазмы: 0–10 / не оценивать;
- влияние на действия: не влияет / немного / сильно / не оценивать;
- контекст: естественный цикл / ранее назначенное подавление / менопауза / другой / не указывать;
- следование ранее назначенной схеме: по плану / был пропуск или изменение / не применимо / не хочу отвечать — только при соответствующем контексте;
- начало эпизода: дата / не помню — необязательное расширение;
- обсудить с врачом; комментарий до 1000;
- доступ: только устройство / назначенный врач.

Менопауза — добровольно сообщённый контекст, не вычисляется по возрасту. Отсутствие выделений при подавлении не вызывает автоматической тревоги. Нет полей назначения препаратов и подсказок по компенсации пропуска.

### Мочевыделительная система — EXT-2, для всех

Поля: есть изменения? → боль/дискомфорт при мочеиспускании; чаще обычного; затруднение; неполное опорожнение; замеченная кровь; другое. Далее общие начало/выраженность/влияние/комментарий/обсудить/доступ. Не повторять одно событие в общей симптоматике с утечкой подробностей.

В первой версии не добавлять ежедневные вопросы о половой жизни, либидо, эрекции и сперме. Дополнительные анатомически специфичные вопросы — отдельное медицински согласованное развитие.

Все персональные поля, их названия в событиях, запрос обсуждения и связанные задания относятся к чувствительной области. Local-only запрос врачу не отправляется скрытно: предложить явно разрешить передачу. Администратор и командир не видят даже число интимных событий.

## 14. Измерения

BASE: пульс, температура, SpO₂ ручным вводом. EXT-1: масса тела. Давление можно добавить отдельным расширением при наличии сценария и прибора.

Общие поля: вид, значение, единица, время наблюдения, контекст, прибор/способ до 100 символов, примечание до 300, source, quality, device_id при наличии. У сохранённого результата есть собственный ID, а не только число внутри анкеты.

Для давления при реализации: систолическое и диастолическое — отдельные значения одного события, единица mmHg; не одна строка для вычислений. Для массы — источник и способ, а не только число.

Ручной ввод quality=unknown. Это допустимый источник, но не «подтверждено датчиком». Технические пределы BASE: пульс 20–250, температура 30–45 °C, SpO₂ 50–100%; это ограничения прототипа, не нормы. За пределами — понятная ошибка без автоматического изменения числа и возможность описать наблюдение в комментарии.

USB: запрос разрешения только по клику; поддержка проверенного desktop-браузера. Состояния отключён → подключён → ожидание контакта → сбор → оценка → результат/неудача. При разрыве не сохранять старое число как новое. Числа в потоковом графике не отправлять до явного сохранения результата.

MAX30102 в этом прототипе — пульс/PPG. Не называть график ЭКГ; SpO₂ не считать достоверной без отдельной валидации. Симулятор всегда помечен, source=simulated.

Прикрепление к дневнику/задаче по ID. Backend проверяет владельца и миссию. Невалидная попытка хранится без итогового числового показателя; не участвует в статистике.

## 15. Активность

«Активность» содержит календарь/список, фильтр периода и кнопку «Добавить тренировку». Вход из задания предзаполняет плановую информацию.

| Поле | Правило |
|---|---|
| Дата и начало | Обязательно, допустим ввод позже события |
| Тип | Аэробная / силовая / другая |
| Тренажёр/способ | Справочник оборудования + другое, необязательно |
| Связанное задание | Необязательно; только своё |
| Плановая длительность | Только из плана, read-only |
| Фактическая длительность | Минуты ≥0; при состоявшейся тренировке >0 |
| Выполнение | Полностью / частично / пропущено |
| Причина отклонения | При частично/пропущено: нет времени / нет оборудования / самочувствие / другое / не хочу указывать |
| Субъективная тяжесть | 0–10 / не оценивать; только если занятие состоялось |
| Дискомфорт | Нет / есть / не оценивать |
| Подробности дискомфорта | При «есть», текст до 500, необязательно |
| Измерения | Выбор сохранённых собственных результатов |
| Комментарий | До 1000 |

Если задания не было: не показывать фиктивный план и процент выполнения. Пользователь фиксирует выполненную тренировку; «пропущено» имеет смысл только относительно заданного/явно указанного плана.

При пропуске фактическая длительность 0, тяжесть и измерения занятия не запрашиваются. При завершении через задачу результат ссылается на activity_id. Нажатие «Открыть тренировку» не выполняет задание.

Врач видит план/факт и комментарии разрешённых записей. Приложение не назначает нагрузки по пульсу автоматически. У пользователя остаётся возможность не передавать запись, но тогда задание нельзя показывать врачу как подтверждённое данным результатом: требуется явное разрешение либо статус результата «не передан».

## 16. Медицинский профиль

«Мой профиль → Здоровье». Не включать в ежедневную анкету.

Поля:
- аллергии: известны / известных нет / сведений нет; без дефолта;
- при известных: вещество/фактор, описание реакции, источник, дата обновления;
- значимые заболевания: список добровольных записей, название/комментарий/источник;
- значимые операции и травмы: событие, дата либо известная точность года/месяца, комментарий;
- ограничения врача: отдельные авторские записи врача, период и причина пересмотра;
- исходные измерения: ссылки на реальные сохранённые значения с датой;
- последнее обновление пользователем;
- последний просмотр/подтверждение врачом.

«Сообщено пользователем» и «проверено врачом» — разные признаки. Проверка привязана к версии и конкретным полям, не общей зелёной галочке профиля. Изменение ранее проверенного поля снимает подтверждение у новой версии, сохраняя историю.

Структурированный ввод лекарств и назначений не входит в этот этап. Не добавлять группу крови, генетические данные, анализ спермы или другие сведения без конкретной функции.

Пользователь видит своих получателей. Данные профиля не становятся доступны администратору. Чувствительные комментарии вынести в защищённую область, а не общий организационный профиль.

## 17. План наблюдения

Единая сущность заданий: измерение / дневник симптомов / тренировка / обследование / консультация / немедикаментозная рекомендация. Тип «Препарат» отсутствует в UI и серверном enum.

Врач → пациент → «План наблюдения» → «Добавить».

Общие поля:
- пациент и миссия — из активного назначения;
- тип — обязательно;
- название 3–120 — обязательно;
- цель до 500 — необязательно;
- инструкция 1–2000 — обязательно;
- начало — обязательно;
- разово/ежедневно; для разового due_at, для ежедневного время, зона и конечная дата;
- дата пересмотра — необязательно;
- ссылка на отчёт/запись — необязательно, проверка доступа;
- видимость general/sensitive.

По типу:
- измерение: показатель, контекст, допустимый способ;
- дневник: наблюдаемые вопросы/симптомы из реализованного словаря;
- тренировка: вид, плановая длительность, оборудование, инструкция;
- обследование: запись обследования из раздела 18;
- консультация: запись консультации из раздела 19;
- рекомендация: инструкция и срок, без схем лекарств.

Обследование/консультация — связанные объекты, а не второй независимый календарь. Изменение их времени обновляет связанную версию плана согласованно. Не создавать по два напоминания об одном событии.

Кнопки: сохранить черновик / предпросмотр / опубликовать / отмена.
Черновик виден только автору. Публикация фиксирует серверное время/автора/версию, но не означает доставки пациенту.

Три независимые группы:
1. Состояние плана: draft/active/completed/cancelled/superseded.
2. Доставка версии: server_saved/device_received/patient_acknowledged.
3. Выполнение экземпляра: pending/done/skipped/unable; overdue — вычисляемый признак.

Ежедневное задание имеет устойчивый occurrence_id на дату расписания. Интервал действия и timezone зафиксированы; смена зоны отображения не переносит срок. Неоднозначное время при смене сезонного времени разрешать явно при публикации, не создавать два экземпляра. UTC по умолчанию упрощает миссионное расписание.

Астронавт: ознакомлен → открыть нужную форму → сохранить результат → подтвердить связь с заданием. Для измерения нужен measurement_id; для дневника checkin_revision_id; для тренировки activity_id. Для консультации/обследования допустимо сообщённое выполнение с отдельным последующим просмотром врача.

«Пропустить»: причина либо отказ указывать. «Не могу выполнить»: комментарий и предложение обратиться к врачу. Эти ответы не подменяют done.

Офлайн выполнение сохраняется локально. Изменение врачом создаёт новую версию с причиной, прошлые инструкции не перезаписываются. Выполнение старой версии после отмены сохраняется как исторический факт с отметкой расхождения; не закрывает новую задачу.

## 18. Обследования

Врач планирует; астронавт сообщает выполнение; врач может подтвердить результат. Самостоятельная запись уже выполненного обследования допустима с маркировкой «Сообщено пользователем».

Плановые поля:
- категория: общий осмотр / зрение / физическая подготовка / лаборатория / стоматология / другое;
- название 3–120;
- пациент/миссия;
- автор;
- плановое время/зона;
- исполнитель/место — необязательно;
- инструкция;
- связанная задача;
- видимость.

Результат:
- фактическое время;
- выполнено / частично / не выполнено;
- причина невыполнения либо «Не указывать»;
- текст результата до 3000;
- показатели — необязательный список: название, значение (число или текст по типу), единица, метод/источник;
- кто внёс и когда;
- врачебный комментарий;
- дата следующего контроля — только явное решение.

Если нет выполненного исследования, нельзя вводить фиктивные показатели. Произвольные файлы, OCT-изображения и PDF лаборатории — NEXT, в первой версии текст и структурированные данные. Не генерировать референсные интервалы и не интерпретировать анализы автоматически.

Статусы расписания planned/rescheduled/cancelled и факт выполнения хранить раздельно. Перенос требует новой даты и причины, старое время остаётся в истории. Отметка пациента «Выполнено» не превращается автоматически в «Результат проверен врачом».

## 19. Консультации и связь с врачом

Врач создаёт плановую консультацию либо отвечает на запрос астронавта.

Поля: пациент, врач, миссия, начало, длительность, зона, формат (синхронная внешняя связь / асинхронный обмен), канал/инструкция, необязательная HTTPS-ссылка, краткая тема, связанные отчёты, general/sensitive.

Для асинхронного обмена вместо обещания видеозвонка показывать период ожидания ответа и текущий статус доставки. Приложение не обязано реализовывать видео: кнопка может открывать согласованный внешний канал с явной подписью.

До консультации астронавт может прикрепить выбранные записи через предпросмотр. Чувствительные сведения не включаются автоматически. Врач не получает локальные черновики.

Статусы: запланирована / перенесена / отменена / состоялась / не состоялась. Вход в страницу/клик на ссылку не означает состоявшуюся консультацию. Завершение фиксирует врач; пациент может сообщить факт участия отдельно.

По завершении врач сохраняет комментарий, запрос уточнения либо новый план наблюдения. В текущем объёме нет назначения препаратов и автоматического клинического заключения.

Сообщение: адресат, тип, текст 1–3000, связанная запись, видимость. Сервер сохранил / устройство получило / пользователь подтвердил прочтение — отдельные события. Врач офлайн не видит ложного «Отправлено»; временный черновик только в памяти с предупреждением о потере при закрытии.

Для скрытых персональных тем уведомление нейтральное: «Новое сообщение врача». Заголовок с симптомом не показывать командиру, администратору или на внешнем экране уведомлений.

## 20. Проверка, история, отчёты

Перед сохранением самоотчёта: период, заполненные секции, пропуски, связанные измерения/тренировки, получатель общей части, получатель персональной, состояние связи. «Изменить» возвращает к разделу без потери остальных значений.

Локальная транзакция сохраняет ревизию, связи и разрешённые операции очереди. Успех только после commit. Нет связи — «Сохранено на устройстве», не ошибка сохранения. Local-only — осознанный режим, не «не удалось синхронизировать».

История: фильтры периода, типа события, источника. Отдельные графики сна, массы, пульса, активности; у жидкости учитывать полноту и длину периода. Не соединять большие пропуски и не заменять их нулями. Не складывать пересекающиеся 24-часовые самоотчёты как независимые суточные объёмы.

Для ежедневных рядов брать актуальную неаннулированную основную запись на local_date, показывать метод отбора. При отсутствии достаточной истории — честный пустой результат. Не объединять автоматически ручной и приборный пульс или разные контексты нагрузки.

Врач видит только доставленные разрешённые данные. Не рисовать число неотправленных записей на борту, если сервер его не знает.

Отчёт: название, период, выбранные версии, получатель, причина, сообщение, отдельное включение чувствительной части. Предпросмотр точно соответствует snapshot. Отправленный snapshot неизменяем; исправление — новая ревизия/дополнение. Включение задания/результата наследует его видимость.

## 21. Единицы EU/US

Настройка пользователя metric/us, по умолчанию metric. Не связана с языком, полом и миссией.

| Показатель | metric | us | Хранение |
|---|---|---|---|
| Температура | °C | °F | °C |
| Масса | kg | lb | kg |
| Рост, если используется | cm | ft + in | cm |
| Выпитая жидкость | mL или L с явной единицей | US fl oz | mL |
| Пульс | уд/мин | уд/мин | bpm |
| SpO₂ | % | % | % |
| Давление при реализации | mmHg | mmHg | mmHg |
| Длительность | минуты/часы | минуты/часы | минуты либо секунды по контракту |

Формулы: F=C*9/5+32; 1 lb=0.45359237 kg; 1 in=2.54 cm; 1 ft=12 in; 1 US fl oz=29.5735295625 mL. Не путать US fluid ounce с Imperial и массовой oz.

Округлять только отображение. Исходное значение/единица и каноническое число сохраняются. Температура/масса/US fl oz — 1 знак, mL — целое для отображения; расчёты используют исходную точность. Повторное переключение не портит данные.

Незавершённый ввод: попросить завершить/очистить поле до переключения. Полный корректный ввод конвертировать, не просто заменить суффикс. Пустые поля остаются пустыми. Старый snapshot отчёта сохраняет свои единицы; динамическая история может показываться в единицах врача.

## 22. Приватность и конфликты разрешений

- Общие медицинские данные приватны по отношению к администратору и командиру.
- Персональный раздел дополнительно требует отдельного согласия на конкретное действующее врачебное назначение.
- Общее согласие и согласие sensitive независимы; sensitive не передаётся при выключенном общем обмене.
- Согласие в настройках предзаполняет выбор, но на проверке записи получатель виден явно.
- Отзыв онлайн закрывает последующее чтение API; офлайн — ожидает доставки и честно это показывает.
- Перед повтором queued-операции перепроверять локальное актуальное разрешение. Отозванную до передачи sensitive-операцию удержать, не отправлять молча.
- Если bundle был согласован как атомарный, нельзя незаметно вырезать sensitive и обозначить весь исходный bundle доставленным. Показать пользователю варианты новой общей отправки.
- Уже доставленные сведения не исчезают из ранее сделанных внешних копий.
- При смене врача старые адресованные отчёты не перепривязываются автоматически.
- Связанные результаты, сообщения, заголовки, экспорт и уведомления наследуют чувствительность.

Не выдавать браузерный офлайн-вход и незашифрованный IndexedDB за защиту реальных медицинских данных. Настоящие персональные медицинские данные — отдельный этап безопасности.

## 23. Offline и backend

На подготовленном устройстве без внешней сети доступны: оболочка, свои записи, черновики, измерения вручную/локальным прибором, полученный план, выполнение заданий, подготовка отчёта, очередь. Не доступны: новые серверные назначения, данные других пользователей, отправка без связи, неполученные изменения врача.

Production build обслуживается локальным HTTP-сервером на фиксированном origin. Если используется PWA — проверенный кеш оболочки; медицинский API не класть в общий HTTP/SW-кеш. Первый вход без предварительной подготовки не поддерживается.

Для каждой операции: operation_id, owner_id, mission_id, schema_version, payload_hash, created_at, состояние/попытки. Для серверного приёма отдельный receipt_id/accepted_at. Повтор того же ID+hash возвращает прежний результат; другой hash — конфликт.

Python API повторяет валидацию, проверяет роли/назначения/согласия/владельца всех связанных ID. Foreign key, unique и транзакции в PostgreSQL поддерживают эти правила. Не полагаться на скрытую кнопку.

Отдельные сущности или эквивалентные модели:
users; missions; memberships; medical_assignments; profile_versions; consents;
checkin_revisions; sensitive_checkin_revisions; measurements; activity_events;
care_plans; care_plan_versions; task_occurrences; task_responses;
examinations; examination_results; consultations; doctor_messages;
report_snapshots; sensitive_report_snapshots; operation_receipts; audit_events.

Не обязательно создавать таблицу для каждого названия, но нельзя смешивать авторство, версии, права и состояния в одном редактируемом объекте без истории.

Новые версии IndexedDB мигрируют без сброса истории/очереди. Серверные миграции не удаляют demo-данные без явной задачи. Отказ одного нового endpoint не должен останавливать независимые BASE-операции. Клиент должен различать неподдерживаемую функцию и временную ошибку.

## 24. Приёмочные сценарии

Для каждой проверки записать build/commit, окружение, действия и доказательство. PASS только для реально выполненного поведения; найденный код не равен успешному сценарию.

| ID | Проверка | Ожидаемое |
|---|---|---|
| E01 | Пользователь без врача | Локальная запись доступна, отчёт не уходит неопределённому адресату |
| E02 | Ежедневная форма | Короткие шаги, можно пропустить необязательные секции |
| E03 | Изменение самочувствия | Сон и питание повторно не обязательны |
| E04 | Сон через полночь | Правильный интервал и длительность |
| E05 | Сон: интервалы + общая оценка | Нет двойного суммирования, источник выбран явно |
| E06 | Жидкость «не отслеживал» | Не превращается в 0 |
| E07 | Частичный учёт жидкости | Метка полноты в истории/отчёте |
| E08 | План питания не задан | Нет вымышленного процента выполнения |
| E09 | Пропущенная тренировка | Нет тяжести нагрузки как будто занятие состоялось |
| E10 | Тренировка из задачи | Один activity_id, один факт выполнения |
| E11 | Самостоятельная тренировка | Нет фиктивного назначения врача |
| E12 | Зрение: нет изменений | Не появляется диагноз/заключение SANS |
| E13 | Персональный раздел off | Нет шага, общая форма работает |
| E14 | Sensitive local_only | Нет содержания в сети, БД сервера и общих сводках |
| E15 | Отзыв до отправки | Операция удержана, нет скрытой передачи |
| E16 | Смена врача | Старый доступ закрыт, новый sensitive не открыт автоматически |
| E17 | Черновик задания | Пациент не видит |
| E18 | Публикация задания | Не означает ознакомление |
| E19 | Ежедневное расписание | Уникальные occurrence_id, нет повторов при синхронизации |
| E20 | Выполнение старой версии | Исторический факт сохранён, новая версия не закрыта |
| E21 | Перенос обследования | Согласованное обновление расписания и истории |
| E22 | Результат пациента | Не помечен «Проверено врачом» |
| E23 | Изменение проверенного профиля | Проверка прежней версии не наследуется молча |
| E24 | Консультация: открыть ссылку | Не помечается состоявшейся |
| E25 | Ответ врача | server_saved/device_received/patient_read различимы |
| E26 | EU/US во время ввода | Корректная конверсия, незавершённый ввод не теряется |
| E27 | US fl oz → mL → обратно | Нет накопления округления и путаницы Imperial/US |
| E28 | Офлайн reload/закрытие вкладки | Черновик, финальная запись и очередь сохраняются |
| E29 | Потеря ответа после commit | Повтор возвращает ту же квитанцию |
| E30 | Другой пользователь входит | Чужая очередь не отправляется от его имени |
| E31 | Чужой measurement/activity ID | Сервер отклоняет операцию |
| E32 | Новый endpoint недоступен | BASE-дневник и независимая доставка работают |
| E33 | Миграция локальной БД | История и pending-очередь сохранены |
| E34 | Архивирование/завершение | Поздние локальные записи не удалены |
| E35 | Симуляция/невалидный прибор | Источник и качество видимы, нет фиктивного числа |
| E36 | Командир/администратор | Прямое медицинское чтение API запрещено |
| E37 | Snapshot отчёта | Последующее изменение исходника не меняет отправленное |
| E38 | Пересекающиеся периоды питания | Нет двойного суточного итога |
| E39 | Общая лента/уведомления | Нет утечки чувствительной темы |
| E40 | Два устройства | Борт офлайн → восстановление → отчёт врачу → ответ → подтверждение |

Минимальная демонстрация: подготовка → ежедневная запись со сном/питанием → тренировка из плана → ручное/реальное измерение → отключение сети → сохранение и reload → восстановление → врач видит разрешённые данные → создаёт уточнение/наблюдение → борт получает. Персональный local-only раздел остаётся только у владельца.

## 25. Порядок внедрения

1. Подтвердить BASE E2E на актуальном backend и production frontend.
2. Добавить расширяемые типы и миграции, проверить обратную совместимость и ACL.
3. Внедрить сон и питание в ежедневную форму; проверить периоды, пропуски и единицы.
4. Внедрить самостоятельные записи активности.
5. Довести версионный план и связи результатов.
6. Добавить профиль здоровья и подтверждение отдельных версий врачом.
7. Добавить обследования/консультации на общем расписании.
8. Добавить зрение/адаптацию и контекст миссии.
9. Проверить отчёты, приватность, отказ новых модулей и полный E2E.
10. Подключить аппаратную часть отдельно и честно зафиксировать ограничения.

Критерий завершения — реальные сценарии, а не наличие пунктов меню. Нет «успешно» при ошибке локального commit, нет «доставлено» без квитанции, нет «ознакомлен» без действия пользователя.
